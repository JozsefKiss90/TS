Hermes · Phase 0 · Lesson 0001 · ~15 minutes

Trace One Request Through an API and a TypeScript SDK

One HTTP request, written twice. By the end you can point at any line and say who owns it: the wire contract, or the library.

Why this matters for Hermes Every loop Hermes will ever run bottoms out in HTTP requests to a model API. Before you can design a ModelGateway, bound a loop, or debug a hung run, you need to see exactly which work belongs to the API (the contract any language must honor) and which work an SDK does for you (and could do wrong, or differently after an upgrade). An SDK you can't see through is magic; Hermes is not allowed to depend on magic.

1 · The raw request

This is a complete call to Anthropic's Messages API using nothing but fetch. The circled numbers mark six responsibilities — remember them, the whole lesson hangs on them.

const controller = new AbortController();                          // ⑥ cancellation

const res = await fetch("https://api.anthropic.com/v1/messages", { // ① endpoint
  method: "POST",
  headers: {
    "content-type": "application/json",
    "x-api-key": process.env.ANTHROPIC_API_KEY!,                   // ② authentication
    "anthropic-version": "2023-06-01",                             // ③ API version
  },
  body: JSON.stringify({                                           // ④ request contract
    model: "claude-opus-4-8",
    max_tokens: 1024,
    messages: [{ role: "user", content: "What is an SDK?" }],
  }),
  signal: controller.signal,
});

if (!res.ok) {                                                     // ⑤ error boundary
  // 401? 429? 529? You write every branch — and every retry — yourself.
  throw new Error(`API error ${res.status}: ${await res.text()}`);
}

const data = await res.json();     // type: any — the compiler knows nothing
console.log(data.content[0].text); // works until the day content[0] isn't text

Everything above is API semantics: the endpoint, the two Anthropic headers, the required body fields, the meaning of a 429. Write this in Python, Rust, or curl and the same rules apply — the contract lives on the wire, not in your language.

2 · The same request through the official SDK

Now the identical request via @anthropic-ai/sdk. Watch where each circled responsibility went.

import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();       // ①+② endpoint baked in; the key is resolved
                                      //     from ANTHROPIC_API_KEY for you
const controller = new AbortController();

try {
  const message = await client.messages.create(
    {
      model: "claude-opus-4-8",       // ④ request contract — now type-checked:
      max_tokens: 1024,               //    delete max_tokens and it won't compile
      messages: [{ role: "user", content: "What is an SDK?" }],
    },
    { signal: controller.signal },    // ⑥ cancellation, plumbed to the transport
  );                                  // ③ version header attached silently;
                                      //    plus retries on 429/5xx and a default timeout

  for (const block of message.content) {
    if (block.type === "text") {      // typed union — narrow before touching .text
      console.log(block.text);
    }
  }
} catch (err) {
  if (err instanceof Anthropic.RateLimitError) {  // ⑤ error boundary — typed classes
    /* back off and retry later */                //    instead of hand-parsed statuses
  } else {
    throw err;
  }
}

Nothing new happened on the wire — the server received byte-for-byte the same kind of request. What changed is who does the chores: the SDK resolves credentials, attaches the mandatory headers, retries connection errors and 408/409/429/5xx responses (twice, by default), applies a request timeout, raises typed errors, and describes the response with TypeScript types so your editor can autocomplete message.content.

The catch that shapes all of Hermes Those beautiful response types are compile-time claims about runtime bytes. TypeScript types are erased when the code runs — the SDK parses whatever JSON arrives and asserts it matches. For the SDK's own responses that's a reasonable bet. For model-generated data — tool arguments, retrieved evidence, task specs — it is not, which is why runtime validation (Zod) is coming in a later lesson. Section 3 dissects exactly how that bet works.

3 · The response types, up close

Hover over message in an editor and TypeScript names its type: Message, an interface shipped in the SDK's generated declaration files (.d.ts). These types aren't hand-written — they are generated from the same API specification the server implements. Abridged:

// @anthropic-ai/sdk — resources/messages (abridged)
interface Message {
  id: string;                      // "msg_015oFa..."
  type: "message";                 // a literal type: can only ever be this string
  role: "assistant";
  model: Model;                    // e.g. "claude-opus-4-8"
  content: Array<ContentBlock>;    // the block union you narrowed in §2:
                                   //   TextBlock | ToolUseBlock | ThinkingBlock | ...
  stop_reason: StopReason | null;  // "end_turn" | "max_tokens" | "stop_sequence"
                                   //   | "tool_use" | "pause_turn" | "refusal"
                                   //   — the list grows as the API evolves;
                                   //   your installed .d.ts is a snapshot
  stop_sequence: string | null;
  usage: Usage;                    // input_tokens, output_tokens,
                                   // cache_read_input_tokens, ...
}

So where does a value of this type come from at runtime? The SDK's pipeline is embarrassingly short:

  1. Bytes arrive off the wire.
  2. JSON.parse turns them into an untyped value. At this instant the compiler knows exactly as much as it did in the raw-fetch version: nothing.
  3. A type assertion — morally parsed as Message — stamps the type on. An assertion is a declaration, not a check: no code compares a single field against the interface.
  4. Everything downstream trusts the label.

That's the phrase unpacked. The claim points in two directions, and only one is enforced:

  • Claims about your code — enforced. Write message.usage.outputTokens instead of output_tokens and it won't compile. Touch .text without narrowing the block and it won't compile. The interface polices everything you write against it.
  • Claims about the bytes — never checked. If the wire delivers a stop_reason value your installed .d.ts predates, or content grows a block type your SDK version has never heard of, the assertion succeeds silently. The surprise surfaces later, wherever your code first trusts the label.

Why does the SDK assert instead of validate? Because for its own responses it's a reasonable bet: the types are generated from the server's own spec, and responsibility ③ — the mandatory version header — pins which revision of the contract the server speaks. Pinning makes drift rare; field-by-field validation of every response would spend code and cycles guarding against it anyway. The same bet is catastrophically wrong for model-generated data — tool arguments, task specs, retrieved evidence — because no version header pins what a model produces. That's the boundary where Hermes will refuse to assert and instead validate, with Zod.
