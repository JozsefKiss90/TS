1 · The lab you just gained

There is a new folder next to lessons/: hermes-sdk-lab/, the home of exercises 01–08. Its configuration is not boilerplate — strict compiler config is Phase 0 material, so read it as content:

hermes-sdk-lab/
├── pnpm-workspace.yaml    ← one install serves every exercise ("0*")
├── package.json           ← shared toolchain: typescript, tsx, @types/node
├── pnpm-lock.yaml         ← the lockfile (see below)
├── tsconfig.base.json     ← the strict config every exercise extends
└── 01-raw-http/
    ├── package.json       ← "type": "module" + the scripts you'll run
    ├── tsconfig.json      ← extends ../tsconfig.base.json
    ├── fixtures/message-response.json   ← the canned response, real shape
    └── src/
        ├── mock-server.ts ← provided — read it, it's this lesson in code
        └── client.ts      ← yours — the TODOs are the exercise

Three configuration ideas carry the whole lab:

  • The lockfile. package.json says what you're willing to accept ("typescript": "^5.7.0" — any 5.x from 5.7 up); pnpm-lock.yaml records what was actually resolved (5.9.3, with the exact version of every transitive dependency). Commit it, and every future install — yours, a teammate's, CI's — reproduces the identical tree. It is the dependency-world version of a recorded fixture: pinned reality, not a range of possibilities.
  • ES modules. "type": "module" in package.json tells Node to treat .js/.ts files as ES modules — import/export with strict, static semantics — rather than legacy CommonJS (require). The tsconfig option module: "nodenext" makes TypeScript resolve imports exactly the way Node will at runtime, so the compiler and the runtime can't disagree about what an import means.
  • Strictness as a contract with yourself. The compiler can only police claims you let it enforce. Each line below tightens what a claim is allowed to hide:
tsconfig lineWhat it refuses to let you hide
strict: trueThe umbrella: no implicit any, and null/undefined are real types you must handle, not surprises.
noUncheckedIndexedAccesscontent[0] is … | undefined — an index can miss at runtime, so the type says so. You will meet this today when you print the first content block.
exactOptionalPropertyTypes“Property omitted” and “property set to undefined” are different things — JSON on the wire has no undefined, so the types keep them apart.
verbatimModuleSyntaxImports must be honest about what survives compilation: types need import type. This is type erasure enforced at the syntax level.
noEmit: trueNothing. It's an admission: we never produce JavaScript files — tsx executes the .ts directly, and tsc is used purely as a checker. Types are erased either way.

2 · A test double for the wire

src/mock-server.ts is a test double: a stand-in that honors the same contract as the real dependency, so the code under test can't tell the difference — and you control both sides. It enforces exactly the checks lesson 0001 circled, and returns either a canned Message (the real response shape, field for field) or a realistic error envelope:

Two honesty notes about what a double can and cannot do:

  • Presence, not authenticity. The mock checks that x-api-key exists — any value passes. Whether a key is genuine only Anthropic's servers can decide. A double can enforce the shape of the contract, never the truths behind it (real keys, real rate limits, real model ids).
  • The base URL is the seam. The contract fixes the path (/v1/messages) but not the host. Your client reads ANTHROPIC_BASE_URL and falls back to localhost:8787 — and the official SDK exposes the very same seam as its baseURL option. That one designed opening is how exercise 02 will aim the genuine @anthropic-ai/sdk at this same mock, unchanged.

3 · The exercise

Commands live in hermes-sdk-lab/01-raw-http/README.md; the arc is:

  1. Install the toolchain. Get pnpm (the README gives a corepack route — admin terminal needed once on this machine — and an npm install -g pnpm fallback), then run pnpm install at the lab root. Open pnpm-lock.yaml afterwards and find typescript in it: that's the range-to-exact resolution from §1, recorded.
  2. Start the mock — terminal 1, in 01-raw-http/: pnpm mock.
  3. Write the request. Fill in src/client.ts — from memory first; the six responsibilities are the checklist, and the mock's error responses are your feedback. Run it with pnpm request (terminal 2) until you see a 200 with stop_reason, the text block, and usage.
  4. Break it, five ways. One change at a time; watch both terminals each run:
BreakWhat you should observe
Delete the x-api-key header401 authentication_error — ② is a header the wire demands, not SDK décor
Delete the anthropic-version header400 invalid_request_error — ③ pins which revision of the contract you speak
Delete max_tokens from the body400 naming the field — ④, and note nothing caught it before the server
Misspell messages in the body400 — the same typo the SDK's types caught at compile time in lesson 0001
Add header x-mock-scenario: rate-limit429 with a retry-after header — the input your ⑤ error boundary should read
setTimeout(() => controller.abort(), 100)An AbortError client-side and an “aborted mid-flight” log server-side — ⑥ works
  1. Close the loop: run pnpm typecheck and ask yourself which of those six failures TypeScript could have caught. (Almost none — you built the body untyped. Hold that thought; it is the entire argument for exercise 02.)
