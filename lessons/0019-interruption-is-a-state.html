Interruption Is a State

A held tool call waits for a human. What is that wait, once the loop is a graph, and who has to stay alive while it lasts?

Why this matters for Hermes This lesson builds scenario step S5 (the loop iterates), where a held tool call queues for the operator. The queue lesson 0010 promised is the set of checkpoints standing at awaiting_approval. Under S3 (dispatch under the graph), the gate is still an edge into that node. The graph file gains nothing, and no process has to wait.

1 · A wait that holds no process

In lessons 0010 and 0018 the operator's answer is a promise. The handler for awaiting_approval races it against the job's bounds, and the process stays alive until one wins. Lesson 0018 killed that process and measured what the checkpoint recovered. The kill was a thrown error, because nothing else could leave the wait.

Here a handler may return a park instead of a move. A parked run is a run stopped at a node by its handler, with no process holding it. The interpreter returns a typed result, and the process may exit.

Part G runs the audit with graph_health held for approval and nobody wired to answer. The model is called once, the gate says hold, and the run parks. The trace file has four lines and the checkpoint file names step 4. Then the process ends.

New today. Three ideas are new.

  • A handler may return a park instead of a move, and a park records nothing.
  • The queue is a filter over the checkpoints, not a record of its own.
  • A verdict is state first and an event later, written by the process that resumes.

2 · The queue is a filter

The approval queue is the set of checkpoints standing at awaiting_approval with no verdict yet. Nothing writes it. Part H lists the checkpoint directory through the strict parse of lesson 0018 and keeps the files that match.

// src/queue.ts                                      // part H, measured
export function parkedJobs(                            bare-audit.json    step 7, landed
  checkpoints: readonly JobCheckpoint[],               parked-audit.json  step 4, awaiting_approval
): JobCheckpoint[] {

The second file comes from the same audit with nothing held, run under the same wiring. Its gate never said hold, so the guard gate_held never opened, and the run never stood at the node. A job that requires no approval cannot enter the queue, whatever the wiring says.

The answer to a parked job is a verdict written into the checkpoint's state. The function is pure, and it refuses three things: a job standing at another node, a job already answered, and a job with nothing pending. The result is a checkpoint again, and the resume reads it back through the same boundary.

Part I is that function at a shell. The trace file is untouched, because no event happened. A verdict in a file is a fact about the job, and the trace holds what the run did.

3 · The resume records the answer

Part J reads the checkpoint back and resumes the run. The handler for awaiting_approval runs again, finds a verdict in the state, and records the approval event. The guard verdict_answered opens, the tool runs, and the job lands after call 2. Resumed before anyone answered, the same handler parks the run again, writes nothing, and the step stays at 4.

The graph did not change, because a node is a place a run can stand, with or without a process.
