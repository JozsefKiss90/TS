The Loop Walks the Graph

Lesson 0017 drew the graph from the supervisor's code. What changes when the graph decides the next move, and the code only does the work?

Why this matters for Hermes This lesson builds scenario step S3 (dispatch under the graph). A job makes only the moves the graph holds, and a move it lacks is refused before it happens. S7 (the run is recorded) gains a second record, a checkpoint, so a job killed mid-run continues where it stopped. The trace holds what happened, the checkpoint holds where the run is, and the graph holds neither.

1 · One step at a time

The supervisor of lab 07 is one function. A loop, three continue statements and fifteen early returns decide what the job does next. The graph file describes those decisions and nothing else. Here each moment's work becomes its own function, and the graph decides.

A node handler is the function that does one node's work and names the node it wants next. It records that node's trace event, the one the walker reads for it, and returns three things.

// src/interpreter.ts                    // the gating handler, measured
export interface Step<S> {                { to: "awaiting_approval",
  to: string;                               state: { …, pending: [{ id: "toolu_1",
  state: S;                                            name: "graph_health", … }],
  event: TraceEvent;                               gate: "hold" },
}                                            event: { kind: "gate", decision: "hold", … } }

A handler never decides whether its move is allowed. The graph interpreter is the loop that runs one handler, checks the move against the graph, writes a checkpoint, and moves.

Terminal nodes have no handler. A run that reaches one ends, and the node's name is the outcome.

New today. Four ideas are new.

  • Each node's work is a handler that names the next node and cannot make the move.
  • The interpreter asks the graph before every move, and a missing edge is a typed refusal.
  • A checkpoint is the state plus the node entered next, replaced after every step.
  • A run killed mid-way resumes from its checkpoint, and that differs from resuming from the trace.

Reprise: the walker and guards (0017), the trace and its resume (0011).

3 · The checkpoint, and what it cannot hold

A checkpoint is the job state plus the node the run enters next, written after every step. The state is the supervisor's local variables, now carried as one value.

// src/job-state.ts, abridged                 // checkpoints/audit-atlas.json, measured
export const JobStateSchema = z.strictObject({   { "job": "Audit the atlas graph",
  transcript: z.array(TurnSchema),                 "step": 4,
  modelCalls, tokensSpent,                         "node": "awaiting_approval",
  toolRuns, alerts, evidenceIds,                   "state": {
  reply: ReplySchema.nullable(),                     "transcript": [ {operator}, {model} ],
  pending: z.array(ToolCallSchema),                  "modelCalls": 1, "tokensSpent": 30,
  results: z.array(ToolOutcomeSchema),               "pending": [ { "name": "graph_health", … } ],
  gate: …nullable(), verdict: …nullable(),           "gate": "hold", "verdict": null,
  exit: …nullable(),                                 "reply": null, "exit": null, … } }
});

The file is replaced on every step. The trace file is appended on every event and never rewritten. One record says where the run is, and the other says what it did. The shape is strict, so an events key is refused at the root, as the graph refuses a claims key.

Three things are not in the file: the deadline timer, the abort controller, and a model call in flight. A resumed run arms a fresh timer. The in-flight call separates the two ways to resume.

Part F kills a run while a held call waits for the operator. The trace has four events and the checkpoint is the one above. The trace rebuild drops the unanswered ask, so the supervisor asks the model again. The checkpoint keeps the ask, so the interpreter asks the operator again.

The tests kill a second run inside call 2, after call_started was written. The trace counts that call, because the provider may have billed it, and resumes at call 3. The checkpoint never heard of it and makes call 2 again. Neither knows what the dead call cost. The one trace now holds two call_started lines in a row, and the walker refuses it at line 7. That refusal is the diagnosis: a call went out and never came back.

7 · Say it in your own words

Answer in the chat after the lab, with no notes.

  1. Say what a handler returns and what it may not decide, with one handler as the example.
  2. Explain what a refusal costs and what it leaves in the trace and in the checkpoint file.
  3. Name one thing only the checkpoint resume recovers, and one thing neither resume recovers.

If you keep only four sentences from this lesson, keep these. A handler does one node's work and names the next node, and the graph decides whether the move is allowed. A move the graph does not hold is refused before it happens, at no cost. A checkpoint is the state plus the node entered next, replaced after every step. A run resumes from its checkpoint at the node it was in, and the trace stays the record of what happened.
