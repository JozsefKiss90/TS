1 · A client is a program

Lesson 0013 drove the server two ways: raw frames from a file, and the Inspector. Neither is a program, and Hermes will be one. It will start the server, run the handshake, and call the tool. An MCP client is that program: it connects to one server over a transport and calls what the server serves.

The SDK ships one as a class. The path is short: import Client, construct it with a name, connect it to a transport, and call callTool.

Four things happen inside connect and callTool that lesson 0013's probe file did by hand.

PieceSyntaxMeaningWhat exists at runtime
client.connect(transport)method, awaitedopen the channel and shake handsa child process, then the initialize frame and the initialized notification

result.structuredContentproperty, typed unknownthe data channelan object the SDK checked against the advertised JSON Schema, and nothing more

A signature tells TypeScript what may be called, and the implementation does the runtime work. The SDK abstracts chores away from your application code, not away from TypeScript. The type of the data channel is unknown, because the SDK cannot know your schema. Your parse is what makes it a bundle.

New today. Five ideas are new.

  • A client is a program, and its data channel arrives typed as unknown.
  • An in-memory transport joins a real client and a real server in one process.
  • The server becomes a function of its port, so a fake can stand behind it.
  • Three guards check one answer, and only two of them run the refinement.
  • A recorded bundle is a fixture: parsed on the way in, replayed through a fake.

2 · The same server, no pipe

The stdio test above takes about a second, most of it spent starting Node and compiling TypeScript. The SDK offers a second channel for tests the pipe has nothing to do with. An in-memory transport is a pair of linked transports that carry frames between a client and a server inside one process.

// tests/server-in-memory.test.ts, the setup
const [clientSide, serverSide] = InMemoryTransport.createLinkedPair();
const client = new Client({ name: "test", version: "0.0.0" });
await buildServer(graph).connect(serverSide);
await client.connect(clientSide);

The frames are the same JSON-RPC messages. The handshake runs. Ids are matched. What is absent is the child process, the pipe, and the rule that stdout belongs to the transport. Measured: five tests over this channel take 141 ms together, and one connect takes 68 ms.

That setup needs the server as a value, not as a file that connects itself at load. So lesson 0014's server.ts split in two. buildServer(graph) registers the tool and the resource over whatever port it is given and returns the server. The wiring file keeps two decisions: which adapter, and which transport.

A fake now fits behind the port. FakeKnowledgeGraph answers from a list it was handed, stamps the bundle with its own name, and records every query. It does not parse its items.

3 · Three guards on one answer

Lesson 0014 measured a rule that does not travel. The two-sources refinement runs in Zod and has no JSON Schema form, so tools/list never carries it. A client exists now, so the guards on its side of the wire can be counted.

GuardWhere it runsChecks againstRuns the refinement?
the server's output parseafter the handler, before the frame leaves the Zod schemayes, and refuses in-band
the SDK client's checkinside callTool, after the frame arrivesthe JSON Schema from tools/listno, because JSON Schema cannot say it
your parseyour code, on structuredContentthe Zod schema, importedyes, and narrows unknown to a bundle

The first guard is testable now without editing the server. A fake holds an item marked confirmed with one source. The item is well typed, so the fake accepts it and the handler returns it. The server's parse refuses the whole answer.

4 · Recorded bundles

Lesson 0012 recorded whole wire exchanges under the model SDK and replayed them. The same move works here, one layer up. The recorder, pnpm record, runs the real adapter under a real client over the in-memory transport. It writes each request and its parsed bundle to fixtures/. The adapter gets a fixed clock, so only recordedAt moves between runs. Re-record, then read the diff.

// fixtures/search-gate.json, abridged           // src/fixtures.ts
{ "recordedAt": "2026-09-20T00:15:02.729Z",      export const RecordedCallSchema = z.object({
  "request": { "name": "search_evidence",          recordedAt: z.iso.datetime(),
               "arguments": { "query": "gate" } },  request: z.object({
  "result": { "query": "gate",                       name: z.literal("search_evidence"),
    "assembledAt": "2026-09-10T09:00:00.000Z",       arguments: z.object({ query: …, limit: … }),
    "assembledBy": { "adapter": "JsonExportAdapter",  }),
                     "snapshot": "dev-graph-2026-09-09" },  result: EvidenceBundleSchema,
    "items": [ … 3 items … ] } }                   });

The loader is a parse, and its schema nests the evidence schema. So the refinement runs on every fixture at load. Measured: a source kind changed to blog is refused at result.items[0].provenance.sources[0].kind, and MOD-003 promoted by hand to confirmed is refused with the two-sources message.

A replay builds a fake from the recording's items and serves it, then calls the recorded request. The items come back equal to the recording. One field differs, and the test says so: assembledBy.adapter now reads FakeKnowledgeGraph, because the fake assembled it this time.
