1 · One command, and everything it must survive

Start where the operator starts — not at the Model Gateway. The first pillar of Hermes OS v1, and the scenario this whole course anchors to, is one read-only command (accepted — PDR-001 §2 pillar 1; Wave 1 is its build target):

hermes rag audit atlas --graph-health --cost-report --no-writeback

The operator asked for a report: how healthy is the atlas project's knowledge graph, what has it been costing, and — by --no-writeback — change nothing while finding out. (The governance form of the command adds --dream-brief, a separate zero-tool reflection step with its own $0.50 ceiling; this walkthrough leaves it aside.) By the end of this supplement you will have followed this request from the operator's keyboard to its persistent evidence, and you will be able to point at the first moment — and it is late — where a Model Gateway is genuinely needed.

Hold one distinction from the start. What Hermes creates from this command is a job, and a Hermes job is not: a prompt, a model request, a Claude Code session, a cron invocation, a tool call, or a chat message. Every one of those may occur inside a job — governed by the job's contract. A Hermes job is a governed unit of work created to achieve a specified outcome: it carries its own operational contract, its own admitted evidence, its own state, its own budget, and it ends in a terminal outcome supported by persistent evidence. §3 makes that structure exact.

New today vs. reprise. Genuinely new ideas — five: ⑴ the Hermes job as the unit of work — envelope + context pack + state + evidence, none of which is a prompt; ⑵ the control plane as fourteen owned responsibilities, most of which are scripts, schemas, checks, or the human — not agents; ⑶ capability routing precedes model routing — "which kind of executor?" is decided before "which model?" ever can be; ⑷ evidence is ten categories with different authority, of which Graph RAG retrieval is exactly one; ⑸ implementation order — the Model Gateway enters only at the first step that genuinely requires probabilistic reasoning, and the real Wave-1 slice reached review with zero model calls. Everything else is reprise: the operational definition of policy (0006a §2), the port/adapter seam (0006), rejection-as-data (0005), the three graphs (course spine), Hermes-orchestrates / Claude-Code-implements (wiki/course/hermes-integration.md).

2 · The system, defined

The definition this supplement will justify piece by piece (proposed clarification — a compression of PDR-001 §§1–3; the PDR's own mission sentence is the accepted form):

The Claude-Assisted Hermes Operating System is a governed job-execution system in which Hermes admits, grounds, plans, routes, supervises, and records work; Claude Code performs bounded repository implementation; deterministic services gather and verify evidence; and the human operator approves consequential change.

v1 is the RAG Factory, not a general AI OS (accepted — D-001). In scope: ontology-grounded RAG project creation, audit, refresh, benchmarking, source and graph validation, context-pack assembly, bounded model reasoning, controlled Claude Code jobs, artifact publication, cost accounting, human-reviewed changes. Out of scope: unrestricted general assistance; unattended code or graph mutation; unbounded multi-agent orchestration (H5+); recursive self-modification; autonomous approval; arbitrary tool access; treating model output as authoritative evidence; silently changing ADRs, memory, skills, budgets, or policies (accepted — D-002, ADR-0014's forbidden levels, ADR-0011/0012's zero-silent-writes family). Every scope dispute defaults to: does it make the factory safer or more observable?

And Hermes is not the OS. Hermes is one operating layer inside it — the persistent controller. The responsibility matrix (accepted — PDR-001 §3, condensed):

When dev_graph intent and code reality disagree, neither wins by rank: the disagreement is Drift, a blocking defect artifact, never auto-resolved (accepted — ADR-0003). That single rule is why the two authorities above stay separate.

3 · The unit of work: what a job actually contains

Two artifacts are mandatory before Hermes may dispatch anything, and both rules are mechanical, not manners (accepted — D-006, D-013, ADR-0002): no envelope → no dispatch; no pack → no dispatch. Script-only (--no-agent) work is pack-exempt — no model interprets context — but never envelope-exempt.

The Job Envelope is the operational contract: eight fields, accepted verbatim (D-013, ADR-0012; encoded in rag_job.schema.json). For the audit job the worked values are the ones Wave-1 issue 02 scaffolded:

Envelope fieldAudit job value (scaffolded)
titlereport-only RAG audit of atlas
ownerThemis — a routing-table row, not a separate agent (ADR-0015)
model policystrong-reasoning class, Anthropic, API-billed only
tool policyread-only allowedTools — no write-capable tool granted
cost ceiling$1 (the audit ceiling; the stricter of command and persona default binds)
output artifact pathvault-relative, under artifacts/reports/
completion conditionreport + evidence bundle filed; blocking harnesses green
cancellation rulekill at ceiling, partial artifact kept; /stop honored

Notice what the envelope is not: it governs execution, but it contains no context, no evidence, no state, no results. Those live elsewhere in the job.

The Context Pack is the admitted evidence bundle (accepted — ADR-0002/0020): canonical nodes, constraints, code truth, permitted docs, and acceptance criteria, assembled by the blueprint's 8-step protocol — semantic retrieval proposes → frontmatter admits → graph traversal expands → filesystem/Git grounds → permitted docs supply — and passing 9 admissibility checks before it is marked admitted: true. Memory may enter only as a labeled advisory block (ADR-0011); CodeGraph evidence enters as a distinct derived-read-only section, downgraded to advisory when its index is stale against Git HEAD (ADR-0004). You met this shape in miniature in lesson 0005: nothing crosses a boundary unvalidated — here the "boundary" is what an agent is allowed to believe.

The whole job, composed (proposed clarification — the accepted record defines every starred part, but no single accepted schema yet composes them into one job object):

6 · The job lifecycle — what is decided, and what is honestly not

Here the record forces this supplement to practice what it preaches. Accepted: job truth lives in manifests, job state files, and the ledger — never in UI state (ADR-0018). Also accepted, as isolated transition facts: admission's accept produces a dispatch record + ledger row; its reject produces a typed refusal and no ledger row; kill-at-ceiling keeps the partial artifact and marks the job failed; an unavailable or over-budget model route means pause + notify, never substitution; /stop kills background work; exit codes are typed (0 pass · 1 findings · 2 usage-error); the terminal words in use are done and failed.

Not accepted anywhere: an enumerated state set. ADR-0018 is titled a task-state policy and deliberately defines only where state lives. 7 · The Spec-to-Evidence Loop, properly

The course has used the phrase since session 1; 0006a drew it as nine moments of the course's system. The general definition (proposed clarification — an operational expansion of the mission sentence):

The Spec-to-Evidence Loop is the governed lifecycle through which Hermes transforms an admitted job specification into a verified terminal outcome supported by persistent evidence.

Expanded into stages, it is §6 with verbs: specify → validate → admit → ground → plan → select capability → execute → verify → decide → record → continue, suspend, or terminate. And the word loop earns its place for one reason only: verification or new evidence can send the job backward — a red harness sends it back to planning; stale topology sends it back to grounding; an unavailable route sends it back to capability selection; ambiguity sends it to human clarification. It is not necessarily a loop of repeated model calls — the audit walkthrough in §8 loops zero times through a model.

What counts as evidence? Far more than Graph RAG retrieval — ten categories, each with its own authority and its own place in the record:

CategoryWhat it groundsAuthority / example
governancewhat may be done at allPDR-001, ADRs, constitutions — ranks 3–4 of the hierarchy
semanticengineering intentcanonical dev_graph nodes passing the 9 checks — rank 5
project & codecurrent realityfilesystem/Git truth — rank 6; CodeGraph topology, derived and advisory-when-stale
source & provenancewhere knowledge came frommanifests: stable ID · checksum · provenance · extraction method · license
retrievalcandidate relevancesemantic search results — they propose, never admit
executionwhat the job didrun logs, typed exit codes, produced artifacts
verificationwhether it countsharness A–H eval_results against the blocking map

operational & costwhat it consumedledger rows, canary reports, cost reports

And the standing separation, restated because this supplement traffics in all three: the knowledge graph (what Hermes knows — dev_graph), the workflow graph (what it may do — envelopes, tool policy, harness gates), and the trace (what it did) never merge. None of the three exists today as an implemented graph database — knowledge is markdown + a read-only Neo4j projection (config-soft, check-verified, not identity-enforced — ADR-0021's own required wording); workflow is schemas + gates; trace is logs + ledger. The separation is a rule about concepts, so that Drift — intent versus reality — stays detectable forever.

8 · The walkthrough: one audit, request to evidence

Now the whole supplement in motion. Twelve moments of hermes rag audit atlas --graph-health --cost-report --no-writeback — for each: who acts, under which policy family, and what evidence moves. Status: moments 1–6 and 9–12 are accepted rules with scaffolded mechanisms (Wave-1 issues 01–06); moments 7–8 are where the record runs out and the labels say so.

  1. Request. The operator asks for a report-only audit. (operator interface; the request is the one human input this job needs until its report lands)
  2. Validation. Hermes builds the eight-field envelope — Themis, strong-reasoning policy, read-only tools, $1 ceiling, vault output path, completion + cancellation rules — and schema-checks it. Incomplete ⇒ typed refusal, no ledger row. (admission policy)
  3. Grounding. Pack assembly gathers, with provenance labels: the governing PDR/ADRs, the project constitution, canonical dev_graph nodes passing the 9 checks, current repository truth, CodeGraph topology (derived section, advisory if stale), the blueprint's requirements, the source manifest, existing eval results, permitted docs. Marked admitted: true. (authority policy — the hierarchy decides what may enter)
  4. Admission. dispatch_gate.py checks all three fail-closed rules: envelope complete, pack admitted, memory-canary green. Accept ⇒ dispatch record + ledger row; the job exists. (scaffolded and tested — Wave-1 issue 01 done)
  5. Decomposition. The flags are the plan: graph-health checks, cost report, no writeback. No dynamic planner runs — v1 decomposition is static per job type. (proposed-clarification territory: "Planner" as a component does not exist)
  6. Deterministic evidence first. Scripts run before any model, per the accepted ordering rule: source-manifest and checksum/provenance checks, ontology validation, frontmatter lint and graph-health composition, retrieval benchmark queries (advisory until ≥30 golden questions), cost-ledger inspection, stale-source checks. Their outputs are the evidence bundle. (routing policy; scaffolded — issues 04–06)
  7. The capability question. For each remaining step the router's sequence runs (§9). Can a script answer it? Done — most of the audit ended at step 6. Is repository implementation required? Not in this job — --no-writeback; a follow-up fix job would dispatch Claude Code, this one may not. Is probabilistic synthesis required? For exactly one kind of step, next. (capability routing — proposed name, accepted ordering)
  8. The first genuine model step. Prioritizing the verified findings, separating fact from hypothesis, explaining implications, drafting the human-readable report — synthesis over an evidence bundle that deterministic tools produced but cannot interpret. Model routing picks the route the envelope's policy allows; the Model Gateway executes that one bounded step and returns a normalized result with usage booked against the remaining ceiling. (planned — the Wave-1 skeleton reached review with zero model calls; this moment is exactly where the gateway will enter, §11)
  9. Verification. The blocking map decides what counts: harnesses C (node health), D (cross-node integrity + the read-only check) and H (Hermes-native discipline — envelope completeness among its five assertions) block; A/B/E/F advise. The read-only proof asserts the audit changed nothing. (completion policy; scaffolded — issue 05, harness wiring issue 09)
  10. Approval. Not needed — nothing mutated, so no approval state is entered. The report may recommend changes; each recommendation becomes a staged proposal for the operator, never an action. (approval + writeback policy)
  11. Terminal. Exit 0 ⇒ completed; exit 1 ⇒ findings — for an audit, findings are the product, so it lands as a successful report that says "unhealthy". Overshooting $1 would have killed it at the ceiling: partial artifact kept, marked failed. (accepted)
  12. Record. Into the vault: the audit report, the context pack used, the evidence bundle, harness results, the cost report, stated limitations. Into the ledger: every booking against the $1. Into the trace: what happened, replayable. The dashboard pages regenerate from these — derivative by construction. (accepted — ADR-0013)

That is the whole OS, and you narrated it without one word of TypeScript. Notice the architectural weight distribution: eleven of twelve moments are deterministic; the model appears once, late, bounded, and optional to the job's validity.

9 · Capability routing before model routing

Lesson 0006's S4 quote — "above it: Hermes policy — routing, provider, model choice" — compresses three separate decisions into one word. Uncompressed:

Capability routing — which kind of executor should perform this step? The decision sequence, in order (the ordering is accepted — ADR-0007's deterministic-first rule and ADR-0012's script-only preference; the component name is proposed):

  1. Can a deterministic operation answer this? → script.
  2. Is authoritative evidence already on file? → read it, run nothing.
  3. Is retrieval required? → retrieval operation (which proposes, never admits).
  4. Is probabilistic synthesis required? → model reasoning — only now does a model enter.
  5. Is repository implementation required? → a Claude Code job.
  6. Is human judgement required? → the operator.
  7. Whatever was chosen: is it currently permitted? → tool policy, budget, approval state.

Model routing — given that a step is approved for model reasoning: which eligible route? Model class by task kind (cheap → classification/dedup; mid → synthesis drafts; strong coding → implementation; strong reasoning → governance review), personas as routing-table rows, API-only billing, and no silent substitution — an unavailable route pauses and notifies (accepted — ADR-0007/0015).

Claude Code dispatch — given that a step needs repository implementation: which bounded, enveloped, context-packed job goes to Claude Code, headless, in a worktree, ending in a PR (accepted — ADR-0001). §10 explains why this is not a third model route.

Three decisions, three owners, three different failure modes. "Routing" without a qualifier is the collision 0006a's policy table warned about, one level up.

10 · The gateways

The two that are easiest to conflate, defined side by side:

The Model Gateway is the bounded access point through which the supervisor executes an already authorized model-reasoning step and receives a normalized result, usage record, and classified failure.

The Claude Code Job Gateway is the bounded dispatch point through which Hermes sends an enveloped, context-packed repository job to Claude Code and receives implementation evidence — diffs, commands, tests, costs, limitations, PR status.

Why Claude Code must not be treated as another model behind the Model Gateway (the boundary is accepted — ADR-0001; this argument is why it exists): a model call is one stateless, tool-less, bounded request that returns text and usage — it has no reach. A Claude Code job is a governed sub-execution: its own envelope, its own tool policy, a worktree, harness gates on its PR, and write reach into a repository. Push it through the model route and every one of those controls evaporates — the tool whitelist, the PR boundary, the blocking map. The gateways differ because the capabilities' blast radii differ.

11 · When the Model Gateway is actually introduced

The course built the gateway in lesson 0006, before admission (0007's TaskSpec), before any evidence machinery. That was the right teaching order — the SDK mechanics were fresh from Phase 0 and the seam needed them. It is not the Hermes OS implementation order. The implementation-order argument, as a dependency sequence:

  1. Select one concrete v1 job — the report-only audit.
  2. Define its requested outcome.
  3. Define its Job Envelope.
  4. Define its states and terminal outcomes.
  5. Define its authority and evidence requirements.
  6. Define the supervisor's responsibilities.
  7. Define capability-routing rules.
  8. Implement deterministic evidence gathering.
  9. Identify the first step that genuinely requires model reasoning.
  10. Introduce the Model Gateway for that step — and not before.

And the empirical anchor (scaffolded, quoted from the Wave-1 record): the real audit walking skeleton reached human review — envelope, admission gate, context pack, graph-health checks, cost report, vault filing, ledger, read-only proof, 310 template tests green — with zero model calls. Steps 1–8 needed no gateway. The first steps that do are synthesis-shaped: prioritizing verified defects, distinguishing facts from hypotheses, explaining implications, drafting the report. Hence the formulation this supplement exists to plant:

The placement rule. The Model Gateway is introduced when an admitted Hermes job reaches a permitted step that requires probabilistic model reasoning and cannot be completed by authoritative retrieval or deterministic tools alone. The course introduces the gateway earlier for TypeScript and SDK pedagogy — that is a teaching order, not the Hermes OS implementation order. "Hermes uses an LLM somewhere" is never, by itself, the reason a Model Gateway exists.

12 · What the Model Gateway owns — and the twelve things it must not

The gateway may: receive an authorized reasoning request; use the already-selected route; execute the bounded operation; return a normalized result; return usage and cost metadata; return model and provider identity; return timing and trace-correlation data; return classified operational failure. Exercise 05 implements exactly this surface in miniature — which is why its supervisor could stay so small.

It must not: create the job; admit the job; assemble the Context Pack; decide which ADR is authoritative; decide whether model reasoning is necessary; decide which tool may execute; define the budget; determine whole-job completion; dispatch Claude Code; approve writeback; merge a PR; persist governance changes. It is not the control loop — it is one organ the loop calls.

One accepted qualification so the compression below is not read too absolutely: on an unavailable or over-budget route the rule is pause + notify (ADR-0007) — the gateway classifies that condition and the supervisor pauses. Detection at the boundary, decision above it — the same split exercise 05 taught for throttled.

Policy constrains.
Router selects.
Gateway executes.
Supervisor decides.
Harness verifies.
Human approves.
Trace records.

And the compression — if you keep only seven sentences from this supplement: ⑴ v1 of the Claude-Assisted Hermes OS is the RAG Factory — a governed job-execution system, not a general AI OS, and Hermes is one layer inside it, never the whole. ⑵ The unit of work is the Hermes job — envelope as contract, Context Pack as admitted evidence, state, budget, evidence, terminal outcome — and it is not a prompt, a model request, or a chat. ⑶ The Job Supervisor owns the lifecycle: every other component acts inside one state and reports facts back. ⑷ Policy is eight enforced families — admission, authority, tool, cost, routing, approval, completion, writeback — each with a mechanical enforcement point, not one vague layer. ⑸ Capability routing precedes model routing: which kind of executor comes first, and deterministic tools run before any model is even nameable. ⑹ The Model Gateway executes exactly one bounded, already-authorized reasoning step and returns a normalized result with usage, identity, timing, and classified failure — twelve upstream and downstream decisions are not its to make. ⑺ A job has landed only when its acceptance conditions are supported by persistent evidence — artifacts in the vault, verdicts from the harnesses, bookings in the ledger, a replayable trace — and, for anything consequential, a human's recorded yes.
