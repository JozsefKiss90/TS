Approval Gates and Permissions

The loop can stop itself since lesson 0009. Which tool calls may run on their own, and which must wait for a human?

Why this matters for Hermes Scenario step S5 (the loop iterates) puts a gate check between every tool call and its run. The audit job ran unattended because its tools only read. Today the job that wants graph_writeback arrives, and no call of that tool runs without an operator's decision. The whole policy is spec data. It sits on the workflow side of the standing rule: what Hermes may do stays apart from what it knows and what it did. In Part H, the operator is you.

1 · Permission gets a third level

Lesson 0008 gave permission two levels. A tool missing from allowedTools is never declared, and a call that names it anyway is refused. A listed tool runs every time, with nobody watching. Two levels were enough while every tool only read.

They are not enough for graph_writeback, which mutates the knowledge graph. Some jobs need it, and no job should run it silently. So the spec gains a middle level: permitted, with every call held for a decision.

"allowedTools":     ["graph_writeback", "graph_health"],   // may be declared to the model
"approvalRequired": ["graph_writeback"]                    // each call waits for the operator

An approval gate is a check that holds a permitted tool call until an operator decides. In the lab it is one pure function, and reading it is reading the whole permission policy:

export type GateDecision = "not_permitted" | "auto" | "hold";

export function gateToolCall(name: string, spec: TaskSpec): GateDecision {
  if (!spec.allowedTools.includes(name)) return "not_permitted";
  if (spec.approvalRequired.includes(name)) return "hold";
  return "auto";
}

Part G runs the gate offline. The fake's first reply carries two calls, and the gate answers "auto" for one and "hold" for the other. A scripted operator denies the held call, and the report shows both decisions:

toolRuns: [ 'graph_health → ran', 'graph_writeback → denied by the operator' ],
outcome: 'landed',  modelCalls: 2,  tokensSpent: 136

One transcript turn still carries both results, in the order the model asked. The denial is a failed result among ordinary ones, and the loop continues. The fake's second reply reports without writing, and the job lands.

The two spec fields can contradict each other. A file that requires approval for a tool it never permitted is refused at admission, by a second refinement, before a token is spent:

.refine((spec) => spec.approvalRequired.every((name) => spec.allowedTools.includes(name)), {
  error: "approvalRequired may only name tools that allowedTools permits",
  path: ["approvalRequired"],
})

New today. Five ideas are new.

  • Permission has a third level: permitted, with every call held for a decision.
  • The whole policy is spec data, and one pure function reads it.
  • The operator is a port, and a missing operator means denial, not approval.
  • A denial answers the model as a failed tool result, so the loop continues.
  • The approval wait races the job's bounds, so a silent operator cannot hang a job.

Reprise: the two readers of allowedTools and refusal-as-answer from lesson 0008, the refinement from lesson 0007, the one controller from lesson 0009, and ports from lesson 0006.

2 · The operator is a port

Who answers a held call? The supervisor does not know, and should not. It asks a port, the same move lesson 0006 made at the model boundary:

export interface ApprovalPort {
  decide(call: ToolCall): Promise<"approved" | "denied">;
}

// a runtime value — Part G's scripted operator (abridged, the lab's also logs):
const denyEverything: ApprovalPort = { decide: () => Promise.resolve("denied") };

// Part H wires your terminal to it instead:
//   approve graph_writeback({"graph":"atlas","patch":"atlas"})? [y/N]

Part G wired a script that denies everything. Part H wires the question above into a live job, so the loop pauses in your terminal until you answer. The wiring decides who the operator is. The supervisor only ever sees the two-valued answer.

When no approver is wired at all, a held call is denied. Default deny is the rule that refuses whatever a policy does not permit. The rule shaped allowedTools in lesson 0007: a spec that says nothing permits no tools. The port applies it again: no channel, no approval. The empty approvalRequired default is deliberately permissive, because a gate is the operator's choice, not a side effect.

Part H ran twice through a logging proxy, denied once and approved once. The two second requests differ in one block and nowhere else:

{ "role": "user", "content": [
    { "type": "tool_result", "tool_use_id": "toolu_mock_0001",
      "content": "The operator declined \"graph_writeback\" for this job.",
      "is_error": true } ] }
// the approved run: "content": "wrote patch to atlas", "is_error": false

No request field records the gate, the wait, or who decided. The human took about four seconds to answer, and the API is stateless, so the late request is just a request. The model cannot tell an operator's denial from a tool failure, except by reading the content text. The denied run cost 229 tokens against the approved run's 221, because the longer denial sentence rides in the resent transcript.

3 · The wait races the bounds

An operator is a human, and humans walk away. Part I wires an approver whose promise never resolves, under a spec with a 2000 ms deadline. The job must still end, because lesson 0009's guarantee also covers a call that waits.

The supervisor already arms one AbortController per job. The approval wait listens to the same signal, so whichever settles first wins:

const verdict = await raceBounds(options.approver.decide(call), signal);
if (verdict === "job_ended") {
  // classified by boundHit: out_of_time, over_budget, or the operator's own abort
}

The measured run ended at about 2018 ms:

outcome: 'out_of_time',  modelCalls: 1,  tokensSpent: 42,
toolRuns: [ 'graph_health → ran', 'graph_writeback → held when the job ended' ],
notes: [ 'deadline of 2000 ms passed while "graph_writeback" waited for approval' ]

The report's first toolRuns line shows the read-only tool had already run before the wait began. Three levels met one unattended job: the read ran, the write waited, and the deadline ended the wait.

7 · Say it in your own words

Answer these in the chat after the lab, with no notes.

  1. Name the three permission levels a tool call can meet, and say where each one is decided.
  2. A reviewer says approvalRequired is redundant, because allowedTools already controls the tools. Answer in two sentences.
  3. Explain why the approval wait must share the job's AbortController rather than waiting freely.

If you keep only four sentences from this lesson, keep these. Permission has three levels: a tool is unlisted, permitted, or permitted with approval, and all three live in the spec. The approval gate holds a call until the operator decides, and a denial answers the model as a failed tool result. The wire has no approval field, so the provider never sees the gate, only its outcomes. The wait races the job's bounds, so a job whose operator never answers still terminates.
