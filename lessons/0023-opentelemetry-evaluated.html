OpenTelemetry, Evaluated

Lesson 0022 built spans by hand. If OpenTelemetry JS emits the same spans, what does the library add, and should Hermes keep it?

Why this matters for Hermes Scenario step S7 (the durable record) gets an export that trace viewers can read. S6 (budget enforcement) gets its alert as a span event. The trace stays the one record of what Hermes did, and it never merges with the workflow graph or the knowledge graph. The win is pnpm job, which reads all seven runs back equal to lab 14's spans, and ADR 0002.

1 · The library meets work you already did

OpenTelemetry is a vendor-neutral standard for traces, with an SDK per language. Lab 15 hands lab 14's spans to it and reads them back. Any difference is a field the library dropped or changed.

An exporter is the SDK object that receives ended spans and sends them somewhere. Lab 15 uses InMemorySpanExporter, which keeps them in an array. OTLP is OpenTelemetry's wire format for sending spans to a trace viewer. A semantic convention is a published list of attribute names and values, so that viewers read one span the same way.

WordIn this courseIn OpenTelemetry
tracethe JSON Lines file of one job's eventsthe spans that share one traceId
spanlab 14's ModelSpan or ToolSpan, computed from two linesan object with ids, a parent, times and attributes
eventone trace line, such as replya named, timed note inside a span, from addEvent

New today. Four ideas are new.

  • A Tracer emits spans, and an exporter receives them.
  • A replayed run must pass every recorded start and end time.
  • OTLP spans carry attribute names from a convention that is not yet stable.
  • A library is judged by which layers it takes over, then recorded in an ADR.

Reprise: the trace (0011), the evaluation shape and ADR 0001 (0020, 0021), spans and costReport (0022).

2 · From TracerProvider to an exported span

The object path has five steps. Import the classes, construct a TracerProvider, ask it for a Tracer, start a span, and end it.

// 15-opentelemetry/src/telemetry.ts
import { InMemorySpanExporter, SimpleSpanProcessor, TracerProvider }
  from "@opentelemetry/sdk-trace";

const exporter = new InMemorySpanExporter();
const provider = new TracerProvider({
  resource: SERVICE,                                   // service.name = "hermes"
  spanProcessors: [new SimpleSpanProcessor({ exporter })],
});
const tracer = provider.getTracer("hermes");

// @opentelemetry/api, the Tracer interface:
startSpan(name: string, options?: SpanOptions, context?: Context): Span;
// Span:
end(endTime?: TimeInput): void;        // TimeInput = HrTime | number | Date
SyntaxMeaningAt run time for audit-atlas's call 1
namethe span's name, built from the operation and the model"chat claude-opus-4-8"
options.startTimewhen the step began, or now if omitted1788134444286, from call_started.at
contextwhich span is the parenta context that holds the job span
end(endTime)closes the span and hands it to SimpleSpanProcessor1788134445940, from reply.at

startSpan has one signature. Its sibling startActiveSpan has three overloads, and each returns whatever its callback returns. Lab 15 does not use it. A signature tells TypeScript what may be called. The implementation does the runtime work. The SDK abstracts chores away from your application code, not away from TypeScript.

The interface lives in @opentelemetry/api, and the work lives in the SDK. With no SDK registered, the API's Tracer records nothing, and its span id is sixteen zeros.

The function exportRun(events, price, tracer) calls lab 14's costReport and emits one job span plus one span per step. Then readBack rebuilds lab 14's span objects from the exporter alone. The test compares the two with toEqual.

3 · What moved, and what did not

On all seven recordings, the spans read back equal lab 14's, field for field. The job totals and agrees match too. So the export loses nothing.

LayerMoved into the library?Measured by
span and trace idsyes, random and new on every exporttwo exports of one file share no id
parent linksyes, from the context passed to startSpanpass no context, and every step becomes a root
time formatyes, [seconds, nanoseconds]round to the second, and seven read-backs fail
exportyes, SimpleSpanProcessor, exporter and the OTLP bodyBatchSpanProcessor holds spans, and 23 tests fail
which lines make a stepno, costReport decidesexportRun calls it first
dollars, remainder, the alert's callno, costReport decidesthe alert becomes a span event at call 2
the recordno, the trace fileids differ per export, so an export cannot replace it

Two traps surfaced in the lab. A span with a given start and no given end ends at Date.now(), so a replayed run lasts until the export. And the SDK's default service name is unknown_service: plus the Node binary's path, which leaks a local path into every export.

Nothing crosses the network in this lab. A real exporter would send this body as POST /v1/traces with Content-Type: application/json. Here it is for call 1, built offline and abridged.

Every gen_ai.* name has status Development, so a rename can arrive without a major version. Lab 15 keeps all names as strings in one file, conventions.ts. A test names the expected strings, because the round trip cannot catch a rename.

4 · The decision

ADR 0002 records it: adopt OTLP as the export format, and keep the trace as the record. The full evidence is in the decision record.

OptionWhat the measurements say
Adopt as the export formatchosen: lossless on seven runs, 147 code lines, and Phoenix, the trace viewer Hermes OS names, accepts OTLP
Wrap behind a portrejected: CostReport is already Hermes's own type, and the API package already separates calling code from the SDK
Skiprejected: Phoenix would need a custom importer for lab 14's report
