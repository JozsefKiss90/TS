Golden Tasks

The loop's tests check its code. What checks a whole run, and how do you know that check can fail?

Why this matters for Hermes Scenario step S9 (score the run) gets its first code. It reads what S8 (outputs land) wrote: one artifact per run. The task file is a JSON boundary, so it is parsed, never trusted. The win: four stored tasks score the real loop at 13 of 13, and each bug added on purpose drops a named check on a named task.

1 · A task written before the run

A golden task is a stored test case for a whole run: a spec, a recorded fixture, the expected ending, and grader names. A grader is a function that reads a landed artifact, its trace and the task, and returns pass or fail with a reason.

Lesson 0012 defined a fixture as recorded data that a test replays. Here the fixture is a trace file. Each reply line holds the text, tool calls, stop reason, token counts and request id. So fixtureFromTrace turns a recorded run into a script for the fake gateway. No reply is typed by hand.

type GoldenTask = {                      // held-audit, after admitGoldenTasks:
  id: string;                            { id: "held-audit",
  spec: TaskSpec;                          spec: { approvalRequired: ["graph_health"], … },
  fixture: string;                         fixture: "../../07-tool-loop/traces/audit-atlas.jsonl",
  operator?: "approves" | "denies";        operator: "approves",
  pack?: AdmittedPack;                     expect: { status: "done", outcome: "landed" },
  expect: { status; outcome };             graders: ["ends_as_expected", "asks_before_held_tool",
  graders: GraderName[];                             "reports_tool_output", "within_ceiling"] }
};

A golden task may expect a failure. capped-audit replays the same recording as audit but allows one model call. A correct loop ends failed (gave_up), and a loop that lands it has a bug.

New today. Five ideas are new.

  • A golden task states the right ending before the run, and that ending may be a failure.
  • A recorded trace is a script the fake gateway can replay.
  • A grader reads what landed and never the loop.
  • A task passes only when every grade on it passes.
  • A bug added on purpose proves that a grader can fail.

Reprise: the fake and the fixture (0006, 0012), the TaskSpec parse (0007), held tools and the operator (0010), guards as names in a file (0017), the artifact and runAndLand (0024).

2 · Graders read what landed

Lab 12's guards have two halves. The graph file names a rule, and guards.ts implements it. Graders copy that shape. The task file names graders, and admitGoldenTasks refuses a name with no function behind it.

// 16-benchmark/src/graders.ts
export interface Seen { task: GoldenTask; artifact: Artifact; events: TraceEvent[] }
export interface Verdict { pass: boolean; why: string }   // { pass: false, why: "no evidence_used line" }
export type Grader = (seen: Seen) => Verdict;
export const GRADERS: Record<GraderName, Grader>;
GraderReadsPasses when
ends_as_expectedartifactstatus and outcome equal the task's expect
reports_tool_outputartifact, traceevery successful tool result appears in the output text
asks_before_held_tooltrace, taskevery held tool's result follows an approved line
uses_the_packtrace, taskthe task's pack is recorded before the first model call
within_ceilingtrace, artifact, taskthe reply lines' tokens match job_ended and the artifact, and stay under the ceiling

Every import in graders.ts is import type, and a test fails if one is not. A grader that called the loop's code could share the loop's bugs and pass them. Hermes OS names the rule "grader ≠ graded".

Anthropic's guide to agent evaluation advises grading what the agent produced, not the path it took. Four graders follow that advice. asks_before_held_tool grades the path, because a held tool that runs early can still produce the right answer.

There is one declaration and no overload. A signature tells TypeScript what may be called. The implementation does the runtime work. Only loop.ts names lab 12. The runner calls the loop it was given, so the graders cannot tell the real loop from a broken copy.

A task passes only when every grade on it passes. The rule matters on the evidence task when the pack is lost. Nothing runs, so nothing is spent, and within_ceiling passes at "0 of 2000 tokens". The other three grades on that task fail, so the task fails.

4 · A grader nobody can fail is untested

A planted defect is a copy of the loop with one bug added on purpose, to prove that some grader fails on it. Lab 16 ships three, each the real loop with one change.

LoopThe one changeTasksGrades that fail
realnone4 of 4none
ignores-approval-listthe spec's held tools are dropped3 of 4held-audit: asks_before_held_tool
ignores-call-capten calls allowed, not one3 of 4capped-audit: ends_as_expected
drops-the-packthe evidence pack never arrives3 of 4grounded-audit: three of four

Under ignores-approval-list, held-audit still ends done with the right answer. Only the path grader sees the bug.

The defects change what the loop is given, not lab 12's code. A hand edit makes the same point in real code. It changed lab 07's gateToolCall to return "auto" for a held tool. Then pnpm bench failed held-audit on asks_before_held_tool alone. The restored code scored 13 of 13.

A bug added to the runner on purpose found a gap in the first draft. Held-audit replayed the parked audit, whose answer is "Audit complete." A loop with no operator wired still passed every grade. The hold was denied by default, the tool result was marked failed, and the model still finished. Held-audit now replays the audit whose answer quotes the tool, and grades reports_tool_output.

5 · The exercise

  2. Run pnpm bench --all. Name the grade each defect drops.
