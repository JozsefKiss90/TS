The Response Becomes a Process

Exercise 02's request gains one field, stream: true. The response stops being a value you await. It becomes a process you watch, and today you stop one mid-way.

Why this matters for Hermes Scenario step S6 (budget enforcement) aborts a model call while the answer is still being written. Text never generated is never billed, so this abort is the budget's enforcement. Today you build and measure it against the mock. The lesson advances lesson 0001's thread of six responsibilities: responsibility ⑥ (cancellation) changes meaning.

1 · One response, many events

The request changes by one body field. The answer changes shape. Instead of one JSON document, the server answers 200 with content-type: text/event-stream and no content-length, because the total length is not known yet.

Server-sent events are a plain-text format for pushing many events over one held-open HTTP response. Each event is an event: line naming a type and a data: line of JSON, separated by blank lines (MDN):

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"Hello from the mock."}}

The event types and their order are fixed (streaming reference). The mock sends the same sequence, readable in both terminals.

New today. Five ideas are new.

  • A response can arrive as many typed events over one held-open connection.
  • Each event carries one slice of the Message, in a fixed order.
  • The prompt's cost arrives first. The ending and the output cost arrive last.
  • The SDK offers raw event iteration and an assembling helper.
  • An abort mid-stream keeps the partial and stops the remainder.

Reprise: the mock and its gates (lesson 0002), narrowing on a type field (lesson 0001), the abort signal (lesson 0003).

2 · Each event carries one slice

The six event types are not interchangeable packets. Each carries one slice of the Message you know from exercises 01 to 03.

EventWhat it carriesWhy there
message_starta Message with id, model and usage.input_tokens, but content: [] and stop_reason: nullwhat the server knows before generating
content_block_startan empty block and its indexopens a slot for deltas to patch
content_block_deltaa text_delta, the next few wordsthe generation itself, as it happens
content_block_stopthe index alonecloses the slot
message_deltastop_reason and the final usage.output_tokenswhat the server knows only after generating
message_stopnothingthe process is over, and the connection closes

A delta is an incremental patch against a message that is still being assembled. Assemble the slices and nothing is missing. Start with message_start's value, append every delta, then add message_delta's two fields. The result is the Message the non-streaming path returns in one piece.

The lab measures it: the assembled text is byte-for-byte exercise 02's fixture, with the same usage and stop_reason. Streaming changes delivery. The response shape does not change.

The order is information. The count usage.input_tokens rides the first event, because the server priced the prompt before answering. The stop_reason and the real output_tokens ride the last events. While a stream is in flight, nobody knows what it will cost or how it will end.

The six responsibilities from lesson 0001 barely move today. The table says which layers changed.

3 · Two SDK surfaces, one wire format

The SDK reads this wire at two levels. Both are declared in the installed .d.ts files, the authoritative description.

// resources/messages/messages.d.ts. The params type picks the overload.
create(params: MessageCreateParamsNonStreaming, ...): APIPromise<Message>;
create(params: MessageCreateParamsStreaming, ...):  APIPromise<Stream<RawMessageStreamEvent>>;

// lib/MessageStream.d.ts. The helper.
declare class MessageStream implements AsyncIterable<MessageStreamEvent> {
  on(event: "text", listener: (textDelta: string, textSnapshot: string) => void): this;
  finalMessage(): Promise<Message>;   // assembles §2's slices for you
  finalText(): Promise<string>;
  get currentMessage(): Message | undefined;  // the partly assembled Message, mid-flight
  get request_id(): string | null | undefined;
  abort(): void;
}

One word now names four things. Keep them apart.

The phraseLevelMeaning
stream: truerequest fieldasks for event delivery on the wire
Stream<RawMessageStreamEvent>return typethe sequence of raw events, one by one
client.messages.stream()methodthe helper's entry point. Its params carry no stream: true
MessageStreamclassthe helper object that assembles the events

An async iterator is an object that yields values one at a time, each one awaited. With stream: true, create() returns one. Every yielded event is a union member, so for await plus narrowing on event.type is lesson 0001's block.type move, one level up. Assembly is your job.

A message stream is the SDK helper that assembles streamed events into a Message for you. The call client.messages.stream(params) returns one. The .on("text") listener receives each chunk and the running total. The finalMessage() method resolves to the assembled Message.

The result of finalMessage() carries _request_id: undefined. Nothing is broken. That object never traveled as one HTTP body, because the helper assembled it client-side from events. The request id belongs to the HTTP exchange, so it lives on the stream object as stream.request_id.

4 · The abort lands mid-process

In exercises 01 to 03, an abort interrupted a wait. Nothing had arrived, so nothing was kept. Today the abort lands in the middle of generation. The lab fires it at 700 ms.

You keep the partial. The text that arrived is yours. There is no stop_reason, because the message never reached its end. The property stream.currentMessage still shows the partly assembled value: two chunks, stop_reason: null.

The remainder is never generated. Against the real API, ungenerated text is unbilled text. Step S6 uses this abort as its enforcement: at the cost ceiling, Hermes stops the answer while the model is writing it.

The SDK does not retry a user abort. The mock logs one attempt, unlike lesson 0003's timeouts.
