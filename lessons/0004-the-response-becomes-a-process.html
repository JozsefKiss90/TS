The Response Becomes a Process

Exercise 02's request with one field added — stream: true — and the response stops being a value you await and becomes a process you observe: typed events arriving over a held-open connection, assembled piece by piece, cancellable in the middle. Same mock, same gates, same Message at the end.

Why this matters for Hermes Phase 1's loop will run for minutes, not milliseconds — streaming is how you watch it work instead of staring at silence. Two policy facts fall out of today's wire format: the numbers Hermes budgets on (stop_reason, real output_tokens) arrive in the last events, and cancellation gains a new meaning — aborting mid-stream stops the remainder from ever being generated, which against the real API means tokens you do not pay for. Budget enforcement needs exactly that lever.

1 · The wire: one response, many events

Nothing changes about the request except one body field. What changes is the answer: instead of one JSON document, the server answers 200 with content-type: text/event-stream and no content-length — because it doesn't know the length yet. The connection stays open, and the body arrives as server-sent events: a dead-simple text format where each event is an event: line naming a type and a data: line of JSON, separated by blank lines (MDN):

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"Hello from the mock."}}

2 · The skeleton and the deltas

The event types are not interchangeable packets — each carries a specific slice of the Message you already know from exercises 01–03:

EventWhat it carriesWhy there
message_starta Message skeleton: id, model, usage.input_tokens — but content: [], stop_reason: nullwhat the server knows before generating: what it read, who is answering
content_block_startan empty block and its indexopens a slot for deltas to patch
content_block_deltaa text_delta — the next few wordsthe actual generation, as it happens
content_block_stopjust the indexcloses the slot
message_deltastop_reason + final usage.output_tokenswhat the server can only know after generating
message_stopnothingthe process is over; the connection closes

Read that first column as a fold: start with the skeleton, apply every delta, retrofit message_delta's fields — and you are holding exactly the Message the non-streaming path returns in one piece. The lab proves it: the assembled text is byte-for-byte exercise 02's fixture, same usage, same stop_reason. Streaming changes delivery, not the contract.

And note the order of knowledge, because Hermes will care: input_tokens is in the first event — the server counted your prompt before answering — but stop_reason and the real output_tokens are in the last ones. While a stream is in flight, nobody knows what it will cost or how it will end.

3 · Two SDK surfaces for one wire format

The SDK gives you the stream at two altitudes — both declared in the installed .d.ts files, which remain the real contract:

// resources/messages/messages.d.ts — the overload is picked by `stream: true`
create(params: MessageCreateParamsNonStreaming, ...): APIPromise<Message>;
create(params: MessageCreateParamsStreaming, ...):  APIPromise<Stream<RawMessageStreamEvent>>;

// lib/MessageStream.d.ts — the helper
declare class MessageStream implements AsyncIterable<MessageStreamEvent> {
  on(event: "text", listener: (textDelta: string, textSnapshot: string) => void): this;
  finalMessage(): Promise<Message>;   // the fold from §2, done for you
  finalText(): Promise<string>;
  get currentMessage(): Message | undefined;  // the fold's state, mid-flight
  get request_id(): string | null | undefined;
  abort(): void;
}
  • Raw events: create({ ...params, stream: true }) hands you an async iterator of RawMessageStreamEvent — a discriminated union, so for await + narrowing on event.type is lesson 0001's block.type skill again, one level up. Accumulation is your job.
  • The helper: client.messages.stream(params) — no stream: true needed; the method is the choice — returns a MessageStream that runs the fold for you: .on("text") gives you delta and snapshot, finalMessage() resolves to the assembled Message.

One trap, measured in the lab: finalMessage()'s result has _request_id: undefined. Nothing is broken — that object never traveled as one HTTP body; the helper assembled it client-side from events. The request id belongs to the HTTP exchange, so it lives on the stream object instead: stream.request_id. Knowing which layer owns which fact is the whole game of SDK literacy.

4 · What ⑥ really means now

In exercises 01–02, cancellation interrupted a wait — abort before the answer, get nothing. Today it interrupts a process. The lab aborts at 700 ms, mid-generation:

Three things to sit with:

  • You keep the partial. The text that arrived is yours; what never arrived simply does not exist. There is no stop_reason — the message did not stop, it was killed.
  • The rest is never generated. Against the real API that is money: a model mid-way through a 4,000-token answer stops costing you the moment the abort lands. Cancellation graduated from a hang-up lever to a cost lever.
  • User aborts are never retried — one attempt in the mock's log, unlike lesson 0003's timeouts. The SDK distinguishes "you chose to stop" from "the network failed you".
