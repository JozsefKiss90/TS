The Trace Is What Happened

The job report dies with the process. What must Hermes write down, and when, so any run can be diagnosed and resumed later?

Why this matters for Hermes Scenario step S7 (the durable trace) is this lesson. Every event of a run appends to a record that outlives the process, and an interrupted run resumes from it. The record answers what happened, kept apart from what Hermes knows and what it may do. Lesson 0010's gate decisions lived in a report that vanishes. Today they land in a file.

1 · A report is a summary. A trace is the record.

Lessons 0008 to 0010 built decisions. Bounds fire, gates hold, operators deny. All of it reaches you as one JobReport printed when the run ends. The process exits, and the story is gone.

A trace is the durable, append-only record of one job's events, written as each event happens. The supervisor already makes every decision the record needs. The change is one emit per moment, each an arm of one schema:

// trace.ts — the event vocabulary, one Zod schema (7 kinds, abridged)
const Reply = z.object({
  kind: z.literal("reply"),
  at: z.number().int().nonnegative(),   // epoch ms, at the moment it happened
  call: z.number().int().positive(),
  stop: z.enum(["completed", "hit_length_cap", "hit_stop_sequence", "wants_tool"]),
  text: z.string(),
  // …calls, inputTokens, outputTokens, requestId
});

export const TraceEventSchema = z.discriminatedUnion("kind", [
  JobStarted, CallStarted, Reply, Gate, Approval, ToolResult, JobEnded,
]);
export type TraceEvent = z.infer<typeof TraceEventSchema>;

// one runtime value, line 4 of Part J's file:
{"kind":"gate","at":1787614192995,"call":1,"tool":"graph_health","decision":"auto"}

Where events land is not the supervisor's business. It appends through a port, the job's third: the model port answers calls, the approval port answers holds, and this one accepts history.

export interface TracePort { append(event: TraceEvent): void }

// the wiring's sink, in main.ts — one JSON line per event:
{ append: (event) => appendFileSync(path, `${JSON.stringify(event)}\n`) }

The moment of writing matters more than the format. The report is built only on a classified exit, so a crashed run reports nothing. The trace is written before the outcome is known, so a crashed run keeps its story up to the cut. The write is synchronous on purpose: appendFileSync returns only after the operating system has the bytes. A buffered writer could lose the tail, and the tail says why.

The file format is JSON Lines: one complete JSON value per line. An append never rewrites earlier lines, so the line number doubles as a sequence number. Part J runs Part A's audit job with a trace wired. The report is unchanged at 217 tokens, and the file holds eight lines:

traces/audit-atlas.jsonl
  job_started → call_started → reply → gate → tool_result
              → call_started → reply → job_ended

New today. Five ideas are new.

  • Every decision the supervisor makes also lands in a trace, at the moment it happens.
  • The trace is the job's third port, and the wiring decides where events land.
  • Reading a trace back is a parse, because bytes on your own disk are still bytes.
  • A resumed job is rebuilt from the file alone: transcript, ledger, and call count.
  • The trace records what happened and decides nothing. Policy stays in the spec.

Reprise: unions narrowed on a discriminant (lessons 0005 to 0009), the boundary parse (lesson 0005), ports (lessons 0006 and 0010), and the partial artifact (lesson 0009).

2 · Reading your own past is a boundary

A trace file is bytes on disk. Any editor, any program, any crash can have touched it since it was written. Lessons 0005, 0007 and 0008 parsed bytes from a provider, an operator and a model. The fourth boundary is your own past: safeParse per line, refuse what fails.

Part K measures it. Run the tight-budget job with a trace, change the final line's "tokensSpent":191 to "tokensSpent":"191", and read the file back:

  +    0 ms  job "Audit the atlas graph under a tight budget" for themis, ceiling 190 tokens
  +    1 ms  model call 1 started
  + 1707 ms  call 1 replied: stop=wants_tool, 23+42 tokens, request req_mock_0001, asks for graph_health
  + 1708 ms  gate: graph_health → auto
  + 1709 ms  tool graph_health → ok: graph=atlas nodes=1284 orphans=3 stale_edges=2
  + 1709 ms  model call 2 started
  line 7 REFUSED: tokensSpent: [invalid_type] Invalid input: expected number, received string
  NOTE: no job_ended — the run crashed, or the record was cut short.

The tampered line is refused with its number, and the other six still read. The refusal is lesson 0005's drift, a string where a number belongs, now on Hermes's own record. And an absence is a finding: call 2 started and never replied, which is where the abort landed.

3 · Resume: the file is enough

Diagnosis reads the trace. Resume replays it. The rebuild folds a run's events back into supervisor state. The transcript comes from reply and tool_result events, the ledger from job_ended, and the call count from call_started. An aborted call still counts, because it was still billed.

Part L measures the round trip. Run 1 carries the tight-deadline spec, and its 2400 ms deadline fires mid-generation of call 2. The run ends out_of_time at 183 tokens booked by estimate, with a 24-character partial artifact kept on the job_ended event. Run 2 starts from the file that run 1 left behind:

rebuilt from the file: { turns: 'operator → model → tools', tokensSpent: 183, modelCalls: 2 }

run 2, resumed:  outcome: 'landed',  modelCalls: 3,  tokensSpent: 335,
                 notes: [ 'stop: completed', 'request: req_mock_0003', … ]

The ledger continued, so 335 is the whole job's spend. The call numbering continued, so the resumed call is call 3. The deadline restarted, because time lost is gone either way, while tokens spent stay spent.

The rebuild replays completed turns only. The partial artifact is kept for the operator, not resent as a turn, because the model never finished saying it. Nobody holds the unwritten remainder. The abort stopped generation before it was produced.

The trace records decisions and never makes them. Deleting a trace changes no future run, and editing one cannot approve a tool, because the gate reads the spec alone. What Hermes may do and what it did stay in separate records, so a disagreement between them stays visible.

If you keep only four sentences from this lesson, keep these. A trace is the append-only record of one job, one event per line, written at the moment each event happens. The file outlives the process, so a finished run can be diagnosed and an interrupted run resumed from the trace alone. Bytes read back from your own disk are still untrusted, so the reader parses every line and refuses what fails. The trace records what happened and decides nothing, because policy lives in the spec and history lives in the file.

Primary source

Read jsonlines.org. The whole format fits on one page: UTF-8, one JSON value per line. Then search the Anthropic Messages API reference for any record of your past requests. The API is stateless, so the only history of a job is the one Hermes writes.

Version pin. Every excerpt and number here was verified against @anthropic-ai/sdk 0.113.0 and zod 4.4.3, by live runs against the exercise 01 mock on a private port. The mock was restarted before each capture, so request ids start at 0001. The mock cannot reason, and its token counts are estimates. The sync append survives the process dying, not the machine losing power. Machine-level durability needs fsync, which the lab skips.
