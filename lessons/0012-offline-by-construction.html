Offline by Construction

The loop works when you watch it run. What proves it still works tomorrow, with no model, no key, and nothing listening on any port?

Why this matters for Hermes Phase 1's exit criterion is this lesson: the loop testable offline, with fakes and recorded exchanges. It builds toward scenario step S9 (scoring the run), which needs runs that repeat on demand. The boundary rule gains a fifth surface, because a recording on disk is bytes. Twenty-nine tests re-prove lessons 0007 to 0011 while no process listens anywhere.

1 · A test proves what its stand-in preserves

An offline test replaces something real with a stand-in, and it proves only what the stand-in preserves. The course has two stand-ins already. The mock server (lesson 0002) is a real HTTP process that doubles the provider at the wire. The fake gateway (lesson 0006) answers at the port from a script, with no socket at all.

The third arrives today. A fixture is recorded data that a test replays in place of the live exchange that produced it. Exercise 08 records four exchanges, derives a fifth, and replays them from then on.

The fixtures reach under the SDK through one constructor option:

// @anthropic-ai/sdk 0.113.0 — client.d.ts, abridged
fetch?: Fetch | undefined;
// internal/builtin-types.d.ts:
type Fetch = (input: string | URL | Request, init?: RequestInit) => Promise<Response>;

Every request the SDK would put on a socket calls this function instead. Auth, retries and SSE assembly still run above it. Below it, nothing exists. A signature tells TypeScript what may be called, and the implementation does the runtime work. Here the implementation is replayFetch in replay.ts: it serves the next recorded response and keeps a copy of what the SDK sent.

The test runner is vitest, and two calls cover this lab. it(name, fn) registers one test. expect(value).toBe(expected) fails that test when the two values differ.

New today. Four ideas are new.

  • A test proves only what its stand-in preserves, so each depth needs its own stand-in.
  • The client's fetch option replaces the socket, so the SDK itself runs under a recording.
  • Fixtures are recorded by the adapter they test, and re-recording turns drift into a diff.
  • One test replays a whole job and holds it to the numbers earlier lessons measured live.

Reprise: the mock (lesson 0002), the fake (lesson 0006), the boundary parse (lessons 0005, 0007, 0008, 0011), and the loop's own measured numbers (lessons 0008 to 0011).

2 · Recorded bytes, with the recorder in the repo

A fixture file holds one exchange: the request the adapter sent, and the response the mock returned.

// replay.ts — the fixture schema, abridged
const RecordedExchangeSchema = z.object({
  scenario: z.string().min(1),
  recordedAt: z.string().min(1),
  request:  z.object({ method: …, path: …, headers: …, body: z.string() }),
  response: z.object({ status: …, headers: …, body: z.string() }),
});

// fixtures/tool-ask.json — one value, abridged
{ "scenario": "call 1 of the audit job: the reply asks for graph_health",
  "request":  { "path": "/v1/messages",
                "body": "{\"model\":\"claude-opus-4-8\",…,\"tools\":[…],\"stream\":true}" },
  "response": { "status": 200,
                "headers": { "request-id": "req_mock_0001" },
                "body": "event: message_start\ndata: {\"type\":\"message_start\",…}\n\n
                         event: content_block_delta\ndata: {…\"text\":\"I\"}\n\n …" } }

Nothing in that file was written by hand. The recorder, record-fixtures.ts, runs the real adapter and supervisor against the exercise 01 mock through a recording fetch. The request is what the adapter sent, and the response body is the SSE stream lesson 0004 dissected, byte for byte. The recorder stays in the repo. One command re-records everything, and a changed mock or adapter shows up as a git diff.

Reading a fixture back is a parse. Lessons 0005, 0007, 0008 and 0011 counted four boundaries: replies, spec files, tool arguments, and your own trace. The fixture file is a fifth, still refused when its bytes fail the schema. Step 4 of the lab tampers one number into a string and reads the refusal.

3 · The capstone, and what it cannot prove

The suite's final test replays exercise 07 Part A's whole job: admission, both model calls, the gate, the tool, the trace. Its base URL names a host that does not resolve, so one socket attempt would fail the test. The report lands with the numbers lesson 0008 measured live: 2 model calls, one tool run, 217 tokens. The trace holds lesson 0011's eight events, in the same order, through an in-memory TracePort.

The supervisor regenerates call 2's request from call 1's replayed reply, and the test compares those bytes to the recording. They match only if the whole chain held: the transcript grew in order, the pairing id came back, the tool output crossed. The lab's step 5 breaks that chain on purpose and watches three tests name it.

Three claims stay unproven. Timing: the fake answers instantly and a replayed stream arrives whole, so the mid-generation abort stays with the live mock. The provider: fixtures freeze the mock, and the mock's error wording is an approximation. Drift on the real wire stays invisible until a live run meets it. The operator: Part H's terminal approval is scripted here, so the port is proven and the human is not.

4 · The exercise

Commands and the measured table live in 08-tested-adapters/README.md. The arc:

  1. Run pnpm test before starting any mock. The pass is the exercise's claim.
  2. Read the supervisor suite beside the adapter suite. For three tests each, say what each one proves that the other cannot.
  3. Open fixtures/tool-ask.json. Find the tool's schema, the invented arguments, and the pairing id the next fixture must carry.
  4. Tamper one recorded number into a string. Predict which test fails before you run.
  5. Comment out the supervisor's model-turn push, run, and read the three failures. Revert.
  6. Re-record against a fresh mock and diff. Only recordedAt should change.

  2. The capstone compares the loop's regenerated second request against the recorded bytes. Say what a mismatch would mean, and name one bug it would catch.

If you keep only four sentences from this lesson, keep these. A test proves only what its stand-in preserves: the fake preserves the port, fixtures preserve the bytes, the mock preserves time. A fixture is recorded data a test replays, and reading one back is still a parse. The recorder lives in the repo, so fixtures can be remade and drift becomes a diff. Green offline tests prove Hermes's side of every contract, and only a live run can prove the provider's.
