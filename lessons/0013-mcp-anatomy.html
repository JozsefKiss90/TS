MCP Anatomy

Lesson 0008 kept every tool inside Hermes. What changes when a tool moves to its own process, behind a protocol?

Why this matters for Hermes Phase 2 builds the evidence supply. This lesson builds toward scenario step S2 (evidence assembled), where Hermes fills a Context Pack by querying the knowledge graph through typed tools. Today that surface exists and answers, with no model anywhere. The boundary rule gains a new surface, because tool arguments now arrive from another process.

1 · The tool leaves the process

Lesson 0008 defined tools as data inside Hermes. Every request carried each tool's name, description and JSON Schema up to the provider. Hermes ran the handler itself. Definition, schema and code lived in one process, and only that process knew the tools existed.

MCP (Model Context Protocol) is an open protocol under which a program serves tools and data to any client that connects. Exercise 09 serves a miniature knowledge graph this way: one tool, search_nodes, over eight nodes in a TypeScript file. The snapshot stands in for the real dev_graph, which is Python-side and stays there.

A resource is data a server publishes under a URI, for a client to read by its own choice. A tool runs when a model asks for an action. A resource answers when a client reads, and no model turn is spent. The graph index is a resource for that reason.

A transport is the channel that carries protocol messages between one client and one server. Exercise 09 uses the standard-io transport: the client starts the server as a child process, writes to its stdin, and reads its stdout. The client owns the server's lifetime, and a closed pipe stops the process.

New today. Five ideas are new.

  • A tool can live in its own process, and clients discover its shape at runtime.
  • A server offers tools for a model's actions and resources for a client's reads.
  • The transport carries JSON-RPC frames, and ids do the matching, not arrival order.
  • One Zod schema both travels to clients and guards the server's own boundary.
  • Failures split into in-band tool refusals and protocol-level errors.

Reprise: tools as data (lesson 0008), the boundary parse (lessons 0005 to 0011), the piped probe (lesson 0002), and the port (lesson 0006).

2 · Frames, not requests

Nothing here is HTTP. JSON-RPC is the message format MCP borrows: one JSON object per message, named by method, matched to its answer by id. On the standard-io transport, one frame is one line. You can therefore drive a server with a text file, and the lab's first step does.

// probe.jsonl → the server's answers, abridged from a measured run
→ {"id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18",…}}
← {"id":1,"result":{"protocolVersion":"2025-06-18",
     "capabilities":{"tools":{…},"resources":{…}},"serverInfo":{"name":"dev-graph-mini",…}}}
→ {"id":2,"method":"tools/list"}
← {"id":2,"result":{"tools":[{"name":"search_nodes",…,
     "inputSchema":{"type":"object",
       "properties":{"query":{"type":"string","minLength":1,…},"limit":{"default":5,…}},
       "required":["query"]}}]}}
→ {"id":4,"method":"tools/call","params":{"name":"search_nodes","arguments":{"query":42}}}
← {"id":4,"result":{"isError":true,"content":[{"type":"text",
     "text":"Input validation error: … expected string, received number"}]}}

The handshake comes first. The client sends initialize, the server answers with its name and capabilities, and the client confirms. Requests flow only after that.

The schema traveled. The minLength, the default and the required list in the reply were generated from the Zod schema at registration. A client learns a tool's shape from the wire, never from your source.

The answers arrived out of order. Our run answered ids 1, 2, 5, 6, 4, 3, because handlers are async and finish when they finish. A response belongs to its request by id, never by position.

Failure uses two channels. Bad arguments come back inside a normal result with isError: true, so a model can read the refusal and try again. An unknown resource URI comes back as a JSON-RPC error object, which is the client's problem, not the model's.

3 · Reading the surface before using it

The whole server is four calls. Import McpServer from @modelcontextprotocol/server, construct it with a name and version, register tools and resources on the instance, then connect a transport.

// @modelcontextprotocol/server 2.0.0 — declarations, abridged
declare class McpServer {
  constructor(serverInfo: Implementation, options?: ServerOptions);
  registerTool<…>(name: string, config: {
    title?: string; description?: string;
    inputSchema?: InputArgs; outputSchema?: OutputArgs; …
  }, cb: ToolCallback<InputArgs>): RegisteredTool;
  registerResource(name: string, uriOrTemplate: string,
    config: …, readCallback: ReadResourceCallback): RegisteredResource;
  registerResource(name: string, uriOrTemplate: ResourceTemplate,
    config: …, readCallback: ReadResourceTemplateCallback): RegisteredResourceTemplate;
  connect(transport: Transport): Promise<void>;
}
PieceSyntaxMeaningWhat exists at runtime
new McpServer({name, version})constructorone server identityan object holding registries, no I/O yet
inputSchema: z.object(…)config propertythe tool's argument shapea Zod schema, converted to JSON Schema once
cbthird argumentwhat the tool doesruns only after the parse admits the arguments
connect(transport)methodattach and servereads stdin from now on, and serves until the pipe closes

registerResource is declared twice, and the return type depends on the second argument. A URI string registers one resource, and the callback receives only the URI. A ResourceTemplate registers a pattern, and the callback also receives the variables parsed from it. TypeScript picks the declaration from what you pass.

A signature tells TypeScript what may be called, and the implementation does the runtime work. The SDK abstracts chores away from your application code, not away from TypeScript. The chores here: schema conversion, the parse before every handler, and frame correlation.

If you keep only four sentences from this lesson, keep these. MCP lets a tool live in its own process and describe itself to any client that asks. A tool acts on a model's request, and a resource answers a client's read at a URI. The Zod schema travels as JSON Schema and guards the server's boundary before any handler runs. Answers match requests by id, and a bad argument fails in-band with isError.
