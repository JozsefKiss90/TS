Validate the Boundary

Exercise 01's client asserted its response type; the SDK asserts more politely; nothing has ever checked. Today the mock's wire quietly stops matching your types, and the main question comes due: when the bytes stop matching the types, which layer notices? Measured answer, before this lesson: none of them.

Why this matters for Hermes Every guarantee Hermes OS makes — no envelope, no dispatch; no Context Pack, no dispatch; zero silent writes — is enforced at a JSON boundary, and today you build the enforcement move. Scenario step S1 Zod-parses the Job Envelope so invalid work is rejected before a single token is spent; S2's admissibility check on the Context Pack is the same parse aimed at evidence. This pays the spine's boundary rule debt opened in lesson 0001 §3 — types are compile-time claims about runtime bytes — and closes Phase 0.

1 · The day the wire breaks its word

Since lesson 0001 every response type in this course has traveled the same pipeline: bytes → JSON.parse → untyped value → assertion → "typed" code. The as MessageResponse in exercise 01 and the SDK's declared Message return type (@anthropic-ai/sdk 0.113.0 — the signature-trace supplement walked it) are the same move at different altitudes: a claim the compiler believes and the runtime never sees, because types are erased before the program runs. The mock can now make the claim false. Send the x-mock-scenario: drift header and the wire answers:

POST /v1/messages
x-api-key: … · anthropic-version: 2023-06-01 · x-mock-scenario: drift

HTTP/1.1 200 OK                        ← a healthy status
content-type: application/json         ← the same media type
request-id: req_mock_0001              ← the same headers

{
  "id": "msg_mock_0001",
  "type": "message",
  …
  "stop_reason": "end-turn",           ← the contract says "end_turn"
  "usage": {
    "input_tokens": 11,
    "output_tokens": "42",             ← the contract says number
    …
  }
}

Run the lab's Part A — exercise 01's pipeline, unchanged — against that response and watch what the course has been warning about since lesson 0001 actually happen. Measured:

typeof output_tokens (TS says number): string
ledger — tokens spent this run: 1142        ← 11 + "42" concatenated as strings
typeof spent (TS says number): string
over the 1000-token ceiling? true           ← a phantom breach; actual spend: 53

No line threw. JavaScript's + met a string and concatenated; the comparison coerced "1142" back to a number; a budget check fired that should never have fired. With different digits the same bug runs the other way — an overrun that never trips. The lie did not crash; it traveled, and surfaced as a wrong number in the one place Phase 1 can least afford one: the ledger that decides when to abort a job.

Account for the layers before reaching for the fix — a claim that "the drift broke X" has to say which layer:

LayerWhat the drift changed thereWhy it cannot object
the six responsibilities ①–⑥nothing — none movedendpoint, auth, version, request contract, errors, cancellation are request- and envelope-side; this lie lives in a successful body

New today vs. reprise. Genuinely new ideas — five: ⑴ a schema is a runtime value that encodes a type; ⑵ parse, don't assert — the check replaces the claim at the boundary; ⑶ a failed parse is data — path-addressed issues a supervisor can act on; ⑷ z.infer derives the static type from the schema — one source of truth; ⑸ validate once, at the edge — typed code carries the proof inward. Everything else is reprise: type erasure (0001), the parse→assert pipeline (0001 §3), narrowing a discriminated union (0001, 0004), the six responsibilities (untouched today), the mock as test double (0002).

2 · The schema is a runtime value

Version pin. Everything below was verified against zod 4.4.3 exactly (no ^/~) — installed declarations in node_modules/zod/v4/classic/ plus live runs against the mock. Schema libraries drift too: issue codes and error formatting are version-specific.

The fix is a library whose entire job is the missing runtime half. Read the entry point the way lesson 0003 read the SDK's — as an object path, one hop at a time:

import { z } from "zod";          // z — a namespace OBJECT. It survives compilation.

const UsageSchema = z.object({    // property access + call → a ZodObject INSTANCE
  input_tokens: z.number().int().nonnegative(),
  output_tokens: z.number().int().nonnegative(),
});

const result = MessageSchema.safeParse(body);   // a method on that instance, fed `unknown`
SyntaxMeaningWhat exists at runtime?
za named import from "zod"an object full of factory functions (typeof z === "object", measured) — compare: an interface leaves nothing
z.object({ … })call a factory with a field mapa ZodObject instance (measured: constructor.name === "ZodObject") holding your field schemas as data
.safeParsemethod lookup on that instancea function bound to the schema value
safeParse(body)invoke with unchecked inputcode that walks the actual bytes' structure and collects every disagreement
z.infer<typeof MessageSchema>a type-level query (§4)nothing — erased; the schema stays, the type is derived from it

The standing distinction, third lesson running: a signature tells TypeScript what may be called; the implementation does the runtime work. Exercise 01's interface was a signature with no implementation anywhere — Zod is the implementation your boundary was missing. And unlike the SDK, which absorbs chores away from your application code, Zod absorbs nothing: it hands you the one chore no SDK will do for you, because only you know which fields your policy relies on.

You have, in fact, already written one of these by hand: the mock's gate ④ (exercise 01) narrows unknown with a page of if-checks — isRecord, "is model a non-empty string", "is max_tokens an integer". A Zod schema is that page, industrialized: declared once, composable, and reporting all failures with paths instead of bailing at the first.

One overloaded word to pin down before it bites — "parse" now means three different operations:

The phraseWhat it checksWhat you getOn failure
JSON.parse(text)JSON syntax onlyan untyped structure (unknown if you are honest)throws SyntaxError
MessageSchema.parse(data)the declared shape, at runtimethe validated, typed valuethrows ZodError
MessageSchema.safeParse(data)the declared shape, at runtimea discriminated union (§3)returns { success: false, error } — nothing thrown
"the parse→assert pipeline" (lessons 0001–0004)syntax, then nothinga claim wearing a typesilence — the lie travels (§1)

And one more collision, preempted: a Zod schema is a runtime validator object in your process. It is not JSON Schema — a serialized description standard you will meet in Phase 2, when MCP tools declare their inputs. Same word, different artifact.

3 · The rejection is data

parse and safeParse are two methods, not an overload — contrast lesson 0004's create(), where one method's return type turned on stream: true. Here you pick by name, and the installed declarations say exactly what each returns (zod/v4/classic/schemas.d.cts, abridged):

parse(data: unknown, …):     core.output<this>;                      // the value — or it throws
safeParse(data: unknown, …): parse.ZodSafeParseResult<core.output<this>>;

// zod/v4/classic/parse.d.cts — the whole union, 10 lines:
type ZodSafeParseResult<T> = ZodSafeParseSuccess<T> | ZodSafeParseError<T>;
type ZodSafeParseSuccess<T> = { success: true;  data: T;       error?: never };
type ZodSafeParseError<T>   = { success: false; data?: never;  error: ZodError<T> };

Read that union and you already know how to use it: narrowing on result.success is the same move as block.type (lesson 0001 §3) and event.type (lesson 0004 §3) — your third discriminated union, and the first where the two arms mean proof and refusal. Beside the declaration, the two runtime values the lab actually produced:

      input_tokens: 11,                                      "stop_sequence", "tool_use"],

Three measured facts to sit with:

  • One parse, every disagreement. Zod collected both lies — it does not stop at the first. An admissibility rejection that names one problem per attempt would take Hermes three round-trips to say what this says in one.
  • Every issue carries a path. ["usage", "output_tokens"] points into the value like a map reference. A rejection is not "invalid input" — it is this field, this reason, machine-readable: loggable to a trace, showable to an operator, S1's "rejected before a token is spent" with reasons attached.
  • The schema out-checked the old type. Exercise 01's interface said stop_reason: string — "end-turn" satisfies that. z.enum([…]) encodes the contract's four words, so the schema caught a lie the type system could not even express a complaint about. For humans, z.prettifyError(result.error) renders the same issues as ✖ lines with → at usage.output_tokens arrows — same data, different audience.

Which method where: parse (throw) fits places where invalid means stop the program — reading your own config at startup. safeParse fits every boundary where invalid is an expected outcome to classify — which is every boundary Hermes owns: the loop must reject the job, record why, and keep supervising, not unwind its own stack.

4 · z.infer turns the arrow around

Until today, the type came first and the bytes were asserted to match. That leaves two artifacts — a hand-written interface and the actual wire — with nothing holding them together; §1 is what the gap looks like. The inversion:

const MessageSchema = z.object({ … });               // the RUNTIME artifact — written once

type Message = z.infer<typeof MessageSchema>;        // the compile-time view — DERIVED
// hover it: { id: string; type: "message"; …; usage: { input_tokens: number; … } }

typeof MessageSchema is TypeScript's type-level handle on the schema value; z.infer extracts from it the type of what a successful parse returns. Delete exercise 01's interface and nothing is lost: the schema now carries both halves — the check that runs at runtime and the type the compiler enforces — so the claim and the check cannot drift apart, because they are one declaration. That is what "single source of truth" means here, and it is the pattern every Hermes contract uses from Phase 1 on: TaskSpec, tool arguments, evidence — schema first, type derived.

Two measured details complete the picture, and two deconfusions fence it:

  • The parse returns the declared subset. Measured in Part C: 9 keys arrived on the wire, 7 crossed the boundary; usage arrived with 4, crossed with 2. z.object strips unrecognized keys by default (its strictObject variant rejects them instead) — so downstream code sees exactly the contract, nothing smuggled. An admissibility-checked Context Pack contains what was declared, full stop.
  • "Validate the boundary" does not mean validate everywhere. One parse where bytes enter; past it, the erased types carry the proof — re-checking inside would redo work the compiler already guarantees. The schema stands at the edge precisely so the interior can stay ordinary typed code.
  • It also does not mean mirror the whole API. Our MessageSchema is deliberately narrower than the SDK's Message — it validates what this client consumes (the ledger's numbers, the text, the stop reason). Phase 1's gateway will do the same: schemas cover the fields policy relies on, not every field the wire might carry.

5 · The exercise

Commands and the full experiment table live in hermes-sdk-lab/04-validate-the-boundary/README.md; the arc is:

  1. Run Part A first — it is given, not TODO. Watch the ledger corrupt without an error, then answer its three closing questions before touching Zod.
  2. Read the contract. Open node_modules/zod/v4/classic/parse.d.cts — the whole ZodSafeParseResult union fits on one screen — then find parse/safeParse side by side in schemas.d.cts. Every §3 claim is on those two pages.
  3. Part B — the parse. Build MessageSchema (the scaffold gives UsageSchema as the pattern), safeParse the drifted body, print every issue's path, code, and message, then z.prettifyError. Count what one parse reported.
  4. Part C — the inversion. Clean wire, successful parse, ledger recomputed from result.data — no as on the whole path. Derive type Message with z.infer and compare the wire's keys against the parsed keys.
  5. Close the loop: say which of the six responsibilities today changed. (Spoiler: none — and that is the point. The boundary check is the responsibility the SDK does not absorb. It stays yours in Phase 1, in Phase 5 when the Agent SDK arrives, always.)

8 · Say it in your own words

After the lab work, close the loop with your teacher. In the chat, answer these four — no notes, no scrolling up:

  1. Define runtime validation in one sentence and type erasure in another — then say why the second makes the first non-optional at a JSON boundary.
  2. Walk the boundary pipeline before and after today: bytes → JSON.parse → ? → typed code. Name exactly what replaced the as, and what that replacement is at runtime.
  3. parse vs safeParse — what does each return, and which one does S1's envelope check want? Why is a rejection that arrives as data with paths worth more to a supervisor than an exception?
  4. Explain the ledger measurement: how did 11 + "42" become a phantom ceiling breach — and why would the same bug with different digits have been worse?

And the compression — if you keep only five sentences from Phase 0's close: ⑴ TypeScript types are erased at runtime; at a JSON boundary they are claims, not checks. ⑵ A Zod schema is a runtime value that checks what the types only claim. ⑶ safeParse returns a discriminated union — typed data on success, path-addressed issues as data on failure. ⑷ z.infer derives the static type from the schema, so the claim and the check cannot drift apart. ⑸ Validate once where bytes enter and trust the types inside — that parse is Hermes's admissibility check: no envelope, no dispatch.
