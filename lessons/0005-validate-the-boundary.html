Validate the Boundary

Every response type in this course so far has been a claim. When the bytes stop matching the types, which layer notices?

Why this matters for Hermes Scenario step S1 (the job envelope is parsed) rejects invalid work before a token is spent. Step S2 (evidence is checked) runs the same parse over a Context Pack. Today you build that parse. It pays the boundary rule opened as debt in lesson 0001, and it closes Phase 0.

1 · The lie that travels

Every response in this course has taken one path. Bytes arrive, JSON.parse checks the syntax, and an assertion attaches a type.

A JSON boundary is the seam where serialized bytes enter your typed code. The as MessageResponse of exercise 01 and the SDK's declared Message return type are the same move at that seam. Both are claims the compiler believes and the runtime never checks, because TypeScript erases types.

The mock can now make the claim false. Send it the header x-mock-scenario: drift.

  "id": "msg_mock_0001",
  "type": "message",
  …

    "input_tokens": 11,

Part A is exercise 01's pipeline, unchanged. Run it against that reply and it prints:

typeof output_tokens (TS says number): string
ledger — tokens spent this run: 1142        ← 11 + "42" joined as strings
typeof spent (TS says number): string
over the 1000-token ceiling? true           ← the run spent 53

No line threw. JavaScript's + met a string and joined the two values. The comparison turned "1142" back into a number, so a budget check fired that should never fire. Other digits run the fault the other way, and a real overrun passes.

New today. Five ideas are new.

  • A schema is a runtime value that encodes a type.
  • A check at the boundary replaces the claim.
  • A failed parse is data, with a path per problem.
  • z.infer derives the static type from the schema.
  • One check at the edge is enough. Typed code carries the proof inward.

Reprise: type erasure from lesson 0001, narrowing a union from 0004, and the mock from 0002.

2 · The schema is a value that runs

Zod supplies the runtime half. Read its entry point as an object path, the way lesson 0003 read the SDK's.

import { z } from "zod";          // z — a namespace OBJECT. It survives compilation.

const UsageSchema = z.object({    // property access + call → a ZodObject INSTANCE
  input_tokens: z.number().int().nonnegative(),
  output_tokens: z.number().int().nonnegative(),
});

const result = MessageSchema.safeParse(body);   // a method on that instance, fed `unknown`
SyntaxMeaningWhat exists at runtime
za named import from "zod"an object of factory functions, where an interface leaves nothing. Measured: typeof z === "object"
z.object({ … })call a factory with a field mapan instance holding your field schemas as data. Measured: constructor.name === "ZodObject"

A Zod schema is a runtime value that encodes a shape. A signature tells TypeScript what may be called. The implementation does the runtime work. Exercise 01's interface was a signature with no implementation anywhere, and Zod is the implementation the boundary was missing.

You have written one of these by hand already. The mock's gate ④ narrows unknown with a page of if checks. A schema is that page, declared once and composable.

One word now names three operations.

The phraseWhat it checksWhat you getOn failure
JSON.parse(text)JSON syntaxan untyped structure, best typed as unknownthrows SyntaxError
MessageSchema.parse(data)the declared shape, at runtimethe validated, typed valuethrows ZodError
MessageSchema.safeParse(data)the declared shape, at runtimea union you narrow, in §3returns { success: false, error } and throws nothing
the pipeline of lessons 0001 to 0004syntax, then nothinga claim wearing a typesilence, as §1 measured

A Zod schema is not JSON Schema, which is a serialized description that travels between programs. Phase 2's MCP tools declare their inputs with it.

3 · The rejection is data

parse and safeParse are two methods, not one overload. Lesson 0004's create() changed its return type when you passed stream: true. Here you choose by name.

// zod/v4/classic/schemas.d.cts, abridged
parse(data: unknown, …):     core.output<this>;                      // the value, or it throws
safeParse(data: unknown, …): parse.ZodSafeParseResult<core.output<this>>;

// zod/v4/classic/parse.d.cts, lines 3 to 13, each member folded onto one line:
type ZodSafeParseResult<T> = ZodSafeParseSuccess<T> | ZodSafeParseError<T>;
type ZodSafeParseSuccess<T> = { success: true;  data: T;       error?: never };
type ZodSafeParseError<T>   = { success: false; data?: never;  error: ZodError<T> };

A safe parse is a check that returns its verdict instead of throwing. You narrow the result on result.success, the same move as block.type in lesson 0001 and event.type in lesson 0004. This is your third such union, and the first whose two arms mean proof and refusal. The lab produced these two values:

  • One parse reported every disagreement. Zod collected both lies and did not stop at the first.
  • Each issue carries a path. ["usage", "output_tokens"] points into the value, so a refusal names the field and the reason.
  • The schema holds rules the old type could not state. Exercise 01's interface said stop_reason: string, and "end-turn" is a string.

z.enum([…]) lists the four words the API allows, so the schema caught a lie the type system could not express. For a human reader, z.prettifyError(result.error) renders the same issues as ✖ lines.

Each method has its place. The throwing one suits reading your own config at startup, where invalid means stop the program. Use safeParse where invalid input is an expected outcome. Hermes must refuse the job, record why, and keep supervising.

4 · The type comes from the schema

Until today the type came first and the bytes were asserted to match. Two artifacts existed, a hand-written interface and the actual reply, with nothing holding them together. §1 measured the gap.

const MessageSchema = z.object({ … });               // the RUNTIME artifact — written once

type Message = z.infer<typeof MessageSchema>;        // the compile-time view — DERIVED
// hover it: { id: string; type: "message"; …; usage: { input_tokens: number; … } }

Schema inference derives the compile-time type from the schema value. TypeScript reads typeof MessageSchema as a handle on that value. The query then extracts the type a successful parse returns.

Delete exercise 01's interface and nothing is lost. One declaration now carries the check and the type, so the two cannot drift apart. Hermes writes the TaskSpec, tool arguments and evidence the same way from Phase 1 on.

The parse also returns the declared subset. Part C measured 9 keys on the wire and 7 across the boundary. Unrecognized keys do not cross, because z.object strips them. z.strictObject refuses them instead.

One parse where bytes enter is the whole rule. Past it the erased types carry the proof, and a second check redoes the compiler's work. The schema also stays narrower than the SDK's Message, and covers only what this client reads.

  2. Name what replaced the as at the boundary, and say what it is at runtime.

If you keep only four sentences from Phase 0's close, keep these. TypeScript types are erased at runtime, so at a JSON boundary they are claims and not checks. A Zod schema checks what a type only claims, and a safe parse returns its verdict as data. The type comes from the schema, so the claim and the check cannot drift apart. Parse once where bytes enter, then trust the types inside.
