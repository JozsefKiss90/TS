The TaskSpec Is a Contract

Exercise 05 called the model with a loose string and a hardcoded token limit. Who decided that job was worth running?

Why this matters for Hermes Scenario step S1 (the envelope check) parses the job first, so Hermes rejects invalid work before it spends a token. Lesson 0005 built that parse and aimed it at a provider's reply. Today the same parse guards the operator's request. The boundary rule now covers both directions into the loop.

1 · The request nobody checked

Open exercise 05's main.ts and find where the job was decided. The prompt is the literal "Hello, Claude!". The size of the call is maxTokens: 100, written inside supervisor.ts. No file records who asked, what the budget was, or where the answer should land.

A running Hermes takes those decisions from an operator, over a command line or a job file. Bytes from an operator are untrusted in the way a provider's reply is untrusted. Nothing in exercise 05 checks them.

New today. Four ideas are new.

  • A schema can describe work, not only bytes from a wire.
  • A parse can decide whether work runs at all.
  • .default() gives one schema two static types.
  • A rule can span two fields, so no single field can carry it.

Reprise: safeParse, path-addressed issues, z.infer, narrowing a union on its tag, and the fake's calls array.

2 · A schema for the work

A TaskSpec is Hermes's schema for one unit of work, written before any model call. It guards a boundary in the same sense lesson 0005's schema did. The bytes reaching it come from an operator instead of a provider.

The course used to call three different things a contract. It now calls one thing a contract. The TaskSpec constrains which work Hermes may run at all. Responsibility ④ is the request and response shape, and gateway.ts is the port. Lessons 0001 to 0005 still carry the older wording until they are rewritten.

export const TaskSpecSchema = z.object({
  title:             z.string().min(1),
  owner:             z.string().min(1),
  instruction:       z.string().min(1),        // becomes ModelCall.prompt
  maxTokens:         z.number().int().positive().max(4096).default(1024),
  costCeilingTokens: z.number().int().positive(),
  allowedTools:      z.array(z.string()).default([]),
  outputPath:        z.string().min(1),
}).refine((spec) => spec.maxTokens <= spec.costCeilingTokens, {
  error: "maxTokens may not exceed the job's costCeilingTokens",
  path: ["maxTokens"],
});

export type TaskSpec      = z.output<typeof TaskSpecSchema>;
export type TaskSpecInput = z.input<typeof TaskSpecSchema>;

A signature tells TypeScript what may be called. The implementation does the runtime work. One declaration here produces two signatures and one implementation. Lesson 0005 needed only z.infer, because that schema had no defaults, and its two types were identical.

3 · The refusal costs nothing

An admissibility check is the parse that decides whether Hermes may dispatch a job. admitTaskSpec is that check. It returns the union shape you narrowed in lesson 0005 for safeParse, and again in lesson 0006 for GatewayResult.

export type Admission =
  | { admitted: true;  spec: TaskSpec }
  | { admitted: false; rejections: string[] };

runTask asks for a TaskSpec, and a successful parse is the only way to obtain one. A caller that skips the check fails to compile. S1's rule therefore holds at build time and at runtime, by two different mechanisms.

no-owner.json → REFUSED, 3 reason(s):
  · title: [too_small] Too small: expected string to have >=1 characters
  · owner: [invalid_type] Invalid input: expected string, received undefined
  · costCeilingTokens: [invalid_type] Invalid input: expected number, received string

not-a-spec.json → REFUSED, 1 reason(s):
  · (root): [invalid_type] Invalid input: expected object, received array

model calls made: 0 — tokens spent: 0

One parse reported every disagreement in the file, which is lesson 0005's behaviour aimed at a new boundary. The mock's counter proves the cost. Against a fresh mock, Part A takes req_mock_0001, a full Part B follows, and the next Part A takes req_mock_0002. No request reached the server while the check refused those files.

4 · The rule no single field can carry

A refinement is a schema rule that runs after every field's type passes. over-ceiling.json sets maxTokens to 4000 against a costCeilingTokens of 1000. Both are positive integers, and both sit inside their declared bounds. The file is still wrong, and z.object cannot say so, because it checks one field at a time.

over-ceiling.json → REFUSED:
  · maxTokens: [custom] maxTokens may not exceed the job's costCeilingTokens

The issue code reads custom, because you wrote the rule rather than declaring a type. The path reads maxTokens, because you chose it. Drop the path option and the issue lands at the root of the object, which names no field an operator can edit.

Order matters here, and it is measurable. A file that omits owner and also breaks the ceiling rule reports the owner issue alone. The refinement never runs, so one bad file can be refused twice, in two rounds.

Answer these in the chat after the lab, with no notes.

  1. Name the two boundaries this exercise parses. Say which direction each one guards, and what arrives at it.
  2. A reviewer says the ceiling rule belongs in runTask, not in the schema. Answer in two sentences.

If you keep only five sentences from this lesson, keep these. A TaskSpec is a schema for the work, and Hermes parses it before the loop calls any model. The admissibility check returns proof or reasons as data, and it refuses without throwing. A refused spec costs zero requests, and Part B measured that against the mock's counter. A default value splits one schema into an input type a file may hold and an output type the loop requires.

Primary source

Read Alexis King's Parse, don't validate, the essay this lesson's gate comes from. Its central move is the one runTask makes: put the guarantee in the type, so the unchecked value cannot travel. Then read Zod's API reference on defaults and refinements.
