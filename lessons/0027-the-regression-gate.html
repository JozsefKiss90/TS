The Regression Gate

The loop passed its tasks yesterday. Which committed file records what passed, and which check refuses a change that does worse?

Why this matters for Hermes S9 (score the run) gains a refusal. It continues the course rule that every JSON boundary gets a runtime check: the committed file is parsed before the gate reads it. The win: four planted defects are refused, and the record of what passed moves only after ten clean runs and an ADR you accepted.

1 · A frozen benchmark and its baseline

A benchmark is a fixed set of golden tasks, their recordings, and the trial counts n and k, named and hashed. Lab 16's is benchmark-v1: lesson 0025's four tasks, with lesson 0026's two recordings for audit, at n = 20 and k = 4.

A score only compares with a score from the same benchmark. A weight of 3 instead of 9 makes audit fail more often, and no loop changed. So the benchmark gets a hash.

// 16-benchmark/src/benchmark.ts, abridged
export function benchmarkHash(taskFile: string): string {
  const text = normalized(taskFile);                  // CRLF read as LF
  const hash = createHash("sha256").update(`${text}\n`);
  for (const recording of recordingsIn(JSON.parse(text)))
    hash.update(`${recording}\n${normalized(resolve(dirname(taskFile), recording))}\n`);
  return `sha256:${hash.digest("hex")}`;              // "sha256:22a1ae48ac33…"
}

The hash reads every recording, not only the task file. A re-recorded fixture is a new benchmark too. Git on Windows may check text out with CRLF line endings, so the hash reads them as LF. Without that line, a test fails.

A baseline is the committed scorecard that every later change to the loop is compared with. It keeps each failed trial by seed and grader, not only a count.

type Baseline = {                    // baselines/benchmark-v1.json, abridged:
  benchmark: string; hash: string;   { "benchmark": "benchmark-v1", "hash": "sha256:22a1ae48…",
  loop: string; n: number; k: number;  "loop": "real", "n": 20, "k": 4,
  adr: string;                         "adr": "docs/adr/0003-freeze-benchmark-v1-as-the-baseline.md",
  tasks: { id; passed; passHatK;       "tasks": [ { "id": "audit", "passed": 19, "passHatK": 0.8,
    failures: { seed;                    "failures": [ { "seed": 4,
      graders }[] }[];                     "graders": ["reports_tool_output"] } ] }, … ] }
};

admitBaseline parses the file with a strict Zod schema before the gate reads it. An unknown key or a missing adr is refused. The file has no clock and is 764 bytes.

New today. Four ideas are new.

  • A hash fixes what a score was measured on.
  • A regression is a trial failure the baseline does not list.
  • A pure gate refuses any change that has one.
  • The baseline moves only by promotion: ten clean runs and an accepted ADR.

Reprise: gateToolCall (0010), golden tasks, graders and planted defects (0025), seeds, pass^k and the parked audit (0026).

2 · The gate refuses a regression

Lesson 0010's gateToolCall reads the spec and answers auto, hold or not_permitted. It runs nothing. The new gate has the same shape, over a scorecard.

A regression is a trial failure that the baseline does not list: the same task, the same seed, and the same grader. A regression gate is a check that refuses a change to the loop when its scorecard has a regression against the baseline.

// 16-benchmark/src/gate.ts
import { gate } from "./gate.js";
const verdict = gate(baseline, { hash, card });   // pure: reads, answers, runs nothing
verdict.ok;                                       // false
verdict.refusals[0];                              // { kind: "regression", task: "held-audit",
                                                  //   seed: 1, grader: "asks_before_held_tool" }

The seed picks the recording, so seed 4 replays the same trial on both sides. A pass count would miss a change that fixes seed 4 and breaks seed 2. That change still scores 19 of 20. A test builds it, and the gate refuses seed 2.

3 · Promotion needs ten clean runs and an accepted ADR

A promotion replaces the baseline. It needs ten consecutive clean runs and an accepted ADR that names the benchmark's hash. The Hermes OS README asks for a signed ADR. Here the signature is the status line, which you set to accepted. Here it guards one course choice: which scorecard becomes the baseline.

promote checks the ADR first. Then it runs the whole benchmark ten times, each run into a fresh folder. A run is clean when it has no regression and writes the same scorecard bytes as run 1.

On a seeded fake, every run of an unchanged loop is the same. So ten runs test the benchmark code and the loop. They ask whether any state leaks from one run into the next. The lab plants a defect that only that test finds.

// 16-benchmark/src/gate-defects.ts, abridged
export function dropsThePackAfter(limit: number): NamedLoop {
  let jobs = 0;                                      // lives as long as the process
  return { name: `drops-the-pack-after-${limit}`, run: (spec, gateway, { pack, ...options }) =>
    REAL_LOOP.run(spec, gateway, ++jobs > limit ? options : { ...options, ...(pack ? { pack } : {}) }) };
}

Each gate run is 80 jobs, so jobs 201 to 240 fall in run 3. One clean gate run is one sample of the code under test. That is lesson 0026's point again, one level up.

Ten clean runs mean more with a live model. Lesson 0026 measured 3,614 passes in 4,000 audit trials. From that, pass^10 is 0.362. A task that fails one time in ten passes ten runs in a row about one time in three.
