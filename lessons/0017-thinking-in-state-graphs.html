Thinking in State Graphs

The supervisor decides what a job does next with if statements. What are the states those statements move between, and can the rules be data?

Why this matters for Hermes This lesson opens Phase 3 and builds scenario step S3 (dispatch under the graph). The loop's control flow becomes data that a parse admits, like the spec and the pack before it. A walker replays the trace of S7 (the run is recorded) against that data, and every recorded run is a path the graph allows. The graph holds no claims and no events, so the knowledge graph, the workflow graph and the trace stay apart.

1 · The states hiding in the code

Every event the supervisor writes to the trace is a moment the run is in. The trace has eight event kinds, and each one enters one state. A workflow graph is the states a job may be in and the moves it may make, held as data.

Trace eventState it enters
job_startedstarted
evidence_usedgrounded
call_startedcalling
replyreplied
gategating
approvalawaiting_approval
tool_resulttool_ran
job_endedits outcome, one of six

An edge is a pair of events the code can write back to back. After a reply, the job lands, a gate decision follows, or the job gives up. Which move is taken depends on the reply's stop reason. A guard is a named rule on an edge that says whether the move is allowed.

Six outcomes end a run and nothing follows them. A terminal node is a state a run may end in, and no edge leaves it. That reading of the supervisor yields 13 states, 26 edges and 6 guards.

New today. Five ideas are new.

  • The loop's states are the nodes its trace events enter, and its branches are edges.
  • The graph is a file of names, admitted by a parse with four rules.
  • A guard is a name in the graph and a function in code.
  • A walker replays a trace along the graph and refuses with a line number.
  • The graph holds no claims and no events, and a strict parse proves it.

Reprise: the safe parse (lesson 0005), the admission union (0007), the trace vocabulary (0011), the fake gateway (0012), the pack's refusal (0016).

2 · The graph as data

The graph is a JSON file with six fields, and every field is a name or a list of names.

// src/workflow-graph.ts, abridged          // graphs/job-lifecycle.json, abridged
const Shape = z.strictObject({               { "name": "job-lifecycle",
  name: z.string().min(1),                     "nodes": ["started", "grounded", "calling", …],
  nodes: z.array(Name).min(1),                 "start": "started",
  start: Name,                                 "terminal": ["landed", "retry_later", …],
  terminal: z.array(Name).min(1),              "guards": ["reply_wants_tool", "reply_finished", …],
  guards: z.array(Name),                       "edges": [
  edges: z.array(z.strictObject({                { "from": "started", "to": "grounded" },
    from: Name, to: Name,                        { "from": "replied", "to": "landed",
    guard: Name.optional(),                        "guard": "reply_finished" },
  })).min(1),                                    … ] }
});

A file is bytes, so a parse admits the graph. The function admitWorkflowGraph(raw: unknown) answers with the graph or with reasons, the union lesson 0007 introduced. Four rules are refinements, because no single field is wrong on its own.

RuleWhy the graph needs itMeasured refusal
the start node is declareda run has to begin somewhere the graph knows start: the start node must be one of the declared nodes
every edge joins declared nodesan edge to a state no event enters can never be takenedges: edge calling > published names a node the graph does not declare
every guard an edge cites is declaredthe walker refuses a graph whose guard it cannot runedges: edge calling > replied cites a guard the graph does not declare: moon_is_full
no edge leaves a terminal nodea job that ended cannot continue edges: edge landed > calling leaves a terminal node

A guard is a name in the file and a function in guards.ts. The name tells the parse which rule an edge needs, and the function does the check at run time. That is lesson 0003's split: a signature says what may be called, and the implementation does the work.

// src/guards.ts                                       // the move it decides
reply_finished:  (leaving) =>                           replied > landed
  leaving.kind === "reply" && leaving.stop !== "wants_tool",
gate_held:       (leaving) =>                           gating > awaiting_approval
  leaving.kind === "gate" && leaving.decision === "hold",

Every guard reads the event being left, because that event decided the branch in the supervisor. None reads the spec, the ledger or the clock.

3 · Replaying the record against the rules

The function walk(graph, guards, events) replays one trace.

PartMeaningAt run time
walkthe replay, exported by walker.tsone loop over consecutive event pairs
graphan admitted workflow graph13 names and 26 edges, read once
guardsfunctions keyed by the names the graph declaressix functions from guards.ts
eventsone trace, parsed by lesson 0011's reader4 to 9 events per recording

For each event it names the node entered, looks for an edge from the current node, and asks the edge's guard. It keeps the current node and the path, and no event. The first missing edge or refused guard ends the walk with a line number.

// src/walker.ts                              // measured, tight-budget.jsonl
export type Walk =                              { ok: true,
  | { ok: true;                                   path: ["started", "calling", "replied",
      path: string[];                                    "gating", "tool_ran", "calling",
      complete: boolean;                                 "over_budget"],
      edgesTaken: string[] }                      complete: true,
  | { ok: false;                                  edgesTaken: ["started>calling", …] }
      line: number;
      from: string;                             // measured, one line moved
      to: string;                               { ok: false, line: 3,
      reason: string };                           from: "calling", to: "grounded",
                                                  reason: "no edge calling > grounded" }

Together they take 10 of the 26 edges. The other 16 come from reading the code, and no recording happened to take them. The tests run the real supervisor against a fake gateway and walk four more, listed in the README.

The graph refuses to hold claims or events, because its shape is strict. Any key the shape does not name fails at the root with unrecognized_keys, so a claims key or an events key is refused.
