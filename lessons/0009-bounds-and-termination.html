Bounds and Termination

Lesson 0008's loop stopped at a hard-coded 4. Who owns the bounds, and what stops a reply that is already being generated?

Why this matters for Hermes Scenario step S6 (the budget is enforced) is the cost guarantee. The job declares a call cap, a token ceiling and a deadline, and the supervisor enforces all three. Responsibility ⑥, cancellation, stops being a cost lever and becomes the enforcement mechanism. You predicted this design after lesson 0004: an in-flight stop must act on an estimate, because the true count arrives last. Today the lab measures your prediction.

1 · The bounds move into the spec

A literal in code is a bound nobody declared. Lesson 0008's MAX_MODEL_CALLS kept the loop correct, but no operator chose it and no spec file could change it. It is gone. The schema from lesson 0007 now carries every bound the loop obeys.

maxTokens:         z.number().int().positive().max(4096).default(1024),
costCeilingTokens: z.number().int().positive(),
maxModelCalls:     z.number().int().positive().max(20).default(4),
deadlineMs:        z.number().int().positive().default(60_000),

Four limits, and they divide cleanly. The provider enforces maxTokens, per call: a reply that reaches it stops with the wire's max_tokens stop reason. Hermes enforces the other three, across the whole job. The two new fields default rather than demand, because a spec that says nothing must still terminate. Here is Part E's spec file, and what an admitted spec becomes:

// specs/tight-budget.json — 6 keys in     // the admitted TaskSpec — 8 keys out
{ "title": "Audit the atlas graph under a tight budget",
  "owner": "themis",
  "instruction": "Summarize the atlas…",
  "maxTokens": 128,
  "costCeilingTokens": 190,               // maxModelCalls: 4   (default)
  "allowedTools": ["graph_health"],       // deadlineMs: 60000  (default)
  "outputPath": "vault/audits/…" }

The report changed with the spec. Termination is the guarantee that a job ends after finitely many model calls, with a classified outcome. The outcome union gains two arms, so a bound that fires is named, not buried in a note:

outcome: "landed" | "retry_later" | "gave_up" | "over_budget" | "out_of_time"

New today. Five ideas are new.

  • Every bound comes from the spec, and every exit is a classified outcome.
  • Enforcement runs at three moments: before a call, during it, and after it.
  • The true cost arrives too late to enforce, so the in-flight check acts on an estimate.
  • One AbortController serves every bound, so cancellation becomes enforcement.
  • An aborted generation still lands, because the partial text is kept.

2 · Enforcement has three moments

The gateway streams every call now. The reason is a single sentence: a bound that is only checked after a reply lands cannot stop the reply. Streaming gives the supervisor a view into a running call, and the port carries that view as a third discriminated union, narrowed on kind:

export type CallProgress =
  | { kind: "call_started"; inputTokens: number }   // e.g. { kind: "call_started", inputTokens: 110 }
  | { kind: "text"; chars: number };                // e.g. { kind: "text", chars: 22 }

Read what the union does not offer: output tokens. The wire explains why. Part E's second call opened with this frame, captured through the logging proxy:

event: message_start
data: {"type":"message_start","message":{…,"content":[],"stop_reason":null,
       "usage":{"input_tokens":110,"output_tokens":1,…}}}

The input count is true from the first frame, because the provider has read the request. The output count is a placeholder, because those tokens do not exist yet. The truth arrives in the last frame of a finished reply:

event: message_delta
data: {"type":"message_delta","delta":{"stop_reason":"tool_use",…},
       "usage":{"output_tokens":42}}

So the supervisor enforces at three moments. Before a call, it refuses to start one when the ledger has reached the ceiling. During a call, it adds booked spend, the call's true input, and an estimated output: one token per three characters seen. Text averages about four characters per token, so dividing by three errs high, and erring high stops a generation early rather than late. After a call, the true counts arrive and the ledger books them.

An aborted call never receives its message_delta, so its true cost never arrives. Part E booked 191 tokens against a ceiling of 190, and the report says the number is an estimate. The check before the next call is what makes the small overshoot safe: a job at its ceiling never starts another call.

3 · One controller, every bound

Lesson 0004 taught the abort as a cost lever: the remainder of an aborted stream is never generated and never billed. Lesson 0009 pulls that trigger from policy. The supervisor arms one AbortController per job, and three hands can fire it:

const bounds = new AbortController();
const deadline = setTimeout(() => { boundHit = "deadline"; bounds.abort(); }, spec.deadlineMs);
const signal = options?.signal
  ? AbortSignal.any([options.signal, bounds.signal])
  : bounds.signal;

The static method AbortSignal.any takes an array of signals and returns one that aborts when any of them does. The operator's signal and the job's own bounds merge into one line to the gateway. The SDK tears the request down when that line fires, as measured in lesson 0004. The abort itself does not say why it happened. The supervisor knows, because it fired the controller, and boundHit records which bound pulled the trigger.

What the abort interrupts is not lost. A partial artifact is the output kept from a generation that was stopped before it finished. The gateway accumulates the streamed text and returns it on the aborted arm, and the report carries it toward S8 (outputs land). Part E kept 46 of 82 characters. Part F, with a 2400 ms deadline, ended at 2424 ms and kept 24. The remainder was never generated and never billed.

outcome: 'over_budget',   tokensSpent: 191,
notes: [ 'budget alert: estimated spend passed 80% of 190',
         'ceiling 190 reached mid-generation; spend is estimated — the true count never arrived',
         'partial artifact kept (46 chars): Audit complete. The tool reported: graph=atlas' ]

Part D closes the triangle offline. The fake answers instantly, so there is no mid-generation to watch, and the cap works between calls. A spec with maxModelCalls: 2 ran against a fake scripted with three tool-hungry replies. The report says gave_up after two calls, and the third scripted reply was never requested.
