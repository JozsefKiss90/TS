Evidence Enters the Loop

The evidence surface answers with provenance, and the loop plans without it. Where does the evidence go, and what stops a job that has none?

Why this matters for Hermes This lesson builds scenario step S2 (evidence assembled) and closes Phase 2. The Phase 1 loop gains a fourth port and asks its questions before it plans. It will not dispatch a job whose evidence never arrived, or whose evidence answers other questions. The claims stay in the knowledge graph. The trace of S7 (the run is recorded) keeps only the ids of the ones a job used.

1 · The loop asks before it plans

A job that must cite the graph needs its answers before the first model call. So the questions belong in the spec, and the answers arrive through a port. An evidence port is that port: a query and a limit go in, and one bundle of items comes back.

// src/context-pack.ts, the port          // 10-graph-evidence: the port below it
export interface EvidencePort {            export interface KnowledgeGraph {
  search(                                    search(q: string, n: number): Promise<EvidenceBundle>;
    query: string,                           node(id: string): Promise<EvidenceItem | undefined>;
    limit: number,                           all(): Promise<EvidenceItem[]>;
  ): Promise<EvidenceBundle>;              }
}

One method, where lesson 0014's port has three. A job being planned only asks questions. The adapter below is lesson 0015's client: import Client, connect it over a transport, call callTool, and parse structuredContent with the evidence schema. The SDK checks the frame against the JSON Schema from tools/list, and the two-sources rule has no JSON Schema form.

No item, no source kind, no confidence label: the evidence schema stays below this line.

New today. Five ideas are new.

  • The loop's fourth port asks for evidence, and one adapter answers over MCP.
  • Several bundles merge into one Context Pack, which carries its own provenance.
  • Four rules decide admissibility, and one of them is lesson 0014's, unrestated.
  • The pack goes into the first turn, so every model call pays for it again.
  • The trace records which evidence a job used, never what the evidence said.

Reprise: the port and its adapter (lesson 0006), the admission union (0007), the spec's default-empty lists (0010), the trace event (0011), the client (0015).

2 · What an admitted pack is

A job asks several questions, and the loop plans from one thing. A Context Pack is that thing: the merged answers to a job's evidence queries, admitted at the boundary before dispatch. The assembler keeps the first match for a repeated id, and records every query.

// src/context-pack.ts, abridged                // one measured pack, abridged
const PackShape = z.object({                     { "job": "Audit the atlas graph",
  job: z.string().min(1),                           "assembledFrom": [
  assembledFrom: z.array(PackQuerySchema)              { "query": "supervisor",
    .min(1),                                             "adapter": "JsonExportAdapter",
  items: z.array(EvidenceItemSchema).min(1),             "snapshot": "dev-graph-2026-09-09",
});                                                      "assembledAt": "2026-09-29T23:33:37.513Z",
                                                         "matched": 1 },
export const ContextPackSchema = PackShape         { "query": "trace", … "matched": 1 }],
  .refine(oneSnapshot, {                            "items": [ { "id": "MOD-004", … },
    error: "a pack must be assembled from …",                   { "id": "MOD-006", … } ] }
    path: ["assembledFrom"] })
  .refine(idsAreUnique, {
    error: "a pack may cite each id once",
    path: ["items"] });

Four rules decide whether the supervisor may dispatch the job. Two are field rules and two are refinements, because no single field is wrong on its own.

RuleWhy the pack needs itMeasured refusal
items has at least one entryno pack, no dispatch: a job that asked and got nothing must not run on guessesitems: [too_small] Too small: expected array to have >=1 items
every row names one snapshottwo snapshots can contradict each other, and the pack could not say which one the job believedassembledFrom: a pack must be assembled from one snapshot of the graph
each id appears oncea repeat pays twice in tokens and reads as two independent confirmationsitems: a pack may cite each id once
every item satisfies the evidence schemathe pack nests it, so lesson 0014's rules run here without being restateditems.0.provenance.confidence: confirmed needs at least two sources

admitContextPack(raw: unknown) answers with the pack or with reasons, and never throws. Lesson 0007's admitTaskSpec returns the same shape. S1 (envelope parsed) admits the job, S2 admits its evidence, and both answers narrow the same way. The assembler builds a candidate typed unknown and hands it over.

A fifth rule lives in the supervisor instead, because the schema never sees the spec. The pack must answer the spec's queries, in that order, and no others. One comparison catches three faults: nothing arrived, the wrong questions were answered, or a pack turned up for a job that asked for none.

3 · Where the pack lands, and what it costs

The pack goes into the first turn, in front of the operator's instruction. One user message, 1,005 bytes in the measured request, holding the rendered pack, a blank line, and the question. It is not a system prompt and not a tool result. Evidence is input to planning, not an answer to a request the model made.

The whole transcript is resent on every call, so every call pays for the pack again. The audit job ran twice against the mock, once grounded and once bare:

RunModel callsTokensInput tokens per call
grounded, 509 characters of pack2494162 then 248
bare, same instruction223633 then 119
the pack's own cost0258129 then 129, so once per call

That is why evidenceLimit is a bound and not a preference.

LayerWhat evidence changes
specevidenceQueries and evidenceLimit, both default-empty, so an older spec file still admits
transcriptthe first turn grows. No new turn kind, and the wire still sees one user message
ledgerinput tokens rise per call, against the same ceiling
traceone evidence_used event, and one more outcome, no_evidence
terminationa job whose pack is missing, or answers other questions, ends before call 1, measured at 0 model calls
gateway, tool catalogue, approval gatenothing. The supervisor never learns what an item or a confidence label is

The event is a reference: queries, snapshot, ids, character count, and no claim text. The ids and the snapshot are enough to read the claims back. The graph holds what Hermes knows, and the trace holds what one job did.
