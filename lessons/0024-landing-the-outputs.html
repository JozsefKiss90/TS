Landing the Outputs

A run ends, crashes, or parks. What must it leave on disk, so that a later reader finds its output, its trace and its cost in one place?

Why this matters for Hermes Scenario step S8 (outputs land, linked to cost) gets its first code. S6 (the budget stops a run) already keeps a stopped call's partial text, and now that text reaches a file. S7 (the durable record) is what every landing reads. The trace stays the one record of what happened, and never merges with the workflow graph or the knowledge graph. The win: all seven recorded runs land, and a crashed run lands too.

1 · A run leaves one folder

An artifact is the folder one run leaves under artifacts/<run>/: its output, its status, and links to its trace and cost report. To land a run is to write its artifact. The folder holds two files, and a reader opens only one of them.

FileWhat it holdsWritten
cost-report.jsonlesson 0022's CostReport, wholefirst
artifact.jsonstatus, outcome, output text, a link to the trace, a link to the cost report, the totalslast, so its presence means the folder is whole

The output already exists in the trace. A finished run's answer is the text of its last reply with stop: "completed". A run that the budget or the deadline stopped keeps its partial text in job_ended.partialText, as lesson 0009 built.

A run that ends over_budget still lands. Its artifact says failed and carries the partial text.

New today. Five ideas are new.

  • Every run leaves one folder, linked to its trace and its cost report.
  • The artifact is computed from the trace file, so a dead process can still land later.
  • A parked run has not ended, so it lands nothing yet.
  • A rename makes a write all or nothing.
  • The file a reader opens is written last.

3 · Every way a run ends

The function landTrace reads a trace file and writes the folder. It reads the file, not the events a run held in memory. That choice decides what a dead process leaves behind.

Lesson 0018's part f killed a run during an approval wait. The process threw, and its code ran no further. A process killed by the operating system runs no code at all. Its trace file is still on disk, so pnpm job --land <trace.jsonl> lands it later, marked failed.

The function runAndLand wraps one run of lab 12's loop. It appends every event to the trace file as it happens. When the run returns or throws, it calls landTrace. A throw still reaches the caller after the landing.

Live run, through startJob and the fakeEndsArtifact

held call with park: trueparkednone until the verdict and the resume, then done

A parked run waits for a verdict, so it has not ended. Its trace and a dead run's trace end the same way: a held gate and no job_ended. The file cannot tell them apart. runAndLand can, because lab 12 returns a typed park.

No trace line names the job. job_started has a title and an owner and no id, so the folder takes the trace file's name. The tight-deadline run and its resume are one job, and they land as two folders.

4 · A kill cannot tear the folder

Lab 12's checkpoint sink calls writeFileSync on the real file at every step. A kill during that call can leave half a JSON document. The next read would fail, and the run's position would be lost.

An atomic write writes a temporary file, then renames it over the target, so no reader sees a half-written file. The rename is one call in node:fs.

// @types/node 22.20.1, fs.d.ts
export function renameSync(oldPath: PathLike, newPath: PathLike): void;

// 14-reliability/src/landing.ts
export function writeAtomic(path: string, text: string, io: AtomicFs = nodeFs): void {
  const temp = `${path}.tmp`;
  io.writeFileSync(temp, text);
  io.renameSync(temp, path);
}

Node's documentation says that rename overwrites an existing target. Linux's rename(2) page also promises the swap is atomic. Windows documents no such promise, so on this machine the guarantee rests on the order of the two steps.

The second rule is order. landTrace writes cost-report.json first and artifact.json last. A reader opens only artifact.json.
