Tool Use, the Loop's Heartbeat

Exercise 06 sent one request and read one answer. What should the supervisor do when the answer is a question?

Why this matters for Hermes Scenario step S5 (the loop iterates) is the job supervisor's core. The model asks for a tool, Hermes decides whether to run it, and the result goes back. Exercise 06 could never reach that step, because it made exactly one call. Today the boundary rule covers a third input: the arguments a model chose. The spec's allowedTools field gets its first reader.

1 · The reply that asks a question

Open exercise 06's supervisor.ts. It calls gateway.complete once, reads the outcome, and returns a report. One job is one request and one answer.

An audit cannot work that way. The model has no access to the atlas graph. It can write about a health report it never saw, or it can ask for one. The API lets it ask, and Hermes answers in the next request.

The model still runs nothing. A reply can request a tool by name. Hermes owns the code, the decision, and the result.

New today. Four ideas are new.

  • A reply can ask for a tool instead of finishing.
  • The answer travels back as a block keyed to the question.
  • The API remembers nothing, so Hermes resends the whole conversation.
  • A short tool list is an offer, and an offer is not enforcement.

2 · Three blocks on the wire

One word does six jobs from here on, so settle the six before reading any wire.

Where you read "tool"What it means there
tools, in the requestthe list Hermes declares this job may use
a tool_use blockone request from the model, naming a tool and its arguments
a tool_result blockHermes's answer to one such request
allowedTools, in the specthe names the operator permitted for this job
tools.tsthe catalogue: descriptions, schemas, and the code that runs
from: "tools"the transcript turn that carries results back

Hermes declares its tools in the request. Each entry carries a name, a description, and an input_schema, which is JSON Schema. The description and the schema are all the model has to work from, so both are part of the interface.

"tools": [{
  "name": "graph_health",
  "description": "Report health counters for one graph: nodes, orphans and stale edges.",
  "input_schema": {"type": "object",
                   "properties": {"graph": {"type": "string", "minLength": 1,
                                            "description": "The graph to inspect…"}},
                   "required": ["graph"]}
}]

The lab writes that schema once, in Zod, and derives three readers from it. The call to z.toJSONSchema() returns a plain object at startup, and offerTools keeps the three fields above. The same Zod schema then parses the arguments that come back, and types the tool's own body. That is lesson 0005's single source of truth, aimed at a third boundary.

A tool_use block is the model's request to run one named tool, with arguments. It arrives inside an ordinary assistant message, next to any text.

"content": [
  {"type": "text", "text": "I need the graph health report first."},
  {"type": "tool_use", "id": "toolu_mock_0001",
   "name": "graph_health", "input": {"graph": "atlas"}}
],
"stop_reason": "tool_use"

A tool_result block carries what the tool returned, keyed to the request it answers. The tool_use_id repeats the id above. Without that key the provider cannot pair the two.

{"role": "user", "content": [
  {"type": "tool_result", "tool_use_id": "toolu_mock_0001",
   "content": "graph=atlas nodes=1284 orphans=3 stale_edges=2", "is_error": false}
]}

Read the role on that message. The wire has no tool role, so a result rides inside a user turn, and the conversation still alternates. The domain calls the turn from: "tools", and anthropic-gateway.ts is the only file that knows the wire's spelling.

3 · The loop, and what it costs

The tool loop repeats until a reply stops asking. In the lab it is one call inside a for, and two turns join the transcript each time round. A turn is a value of this type, declared in gateway.ts:

export type Turn =
  | { from: "operator"; text: string }
  | { from: "model"; text: string; calls: ToolCall[] }
  | { from: "tools"; results: ToolOutcome[] };

Part A's transcript, at the moment of the second request:

[ { from: "operator", text: "Summarize the atlas graph health check…" },
  { from: "model",    text: "I need the graph health report first.",
                      calls: [{ id: "toolu_mock_0001", name: "graph_health",
                                input: { graph: "atlas" } }] },
  { from: "tools",    results: [{ id: "toolu_mock_0001", failed: false,
                                  output: "graph=atlas nodes=1284 orphans=3 stale_edges=2" }] } ]

Three arms, narrowed on from, which is the union shape you met in lesson 0005 and again in lesson 0006. The adapter turns each arm into a message, and only the adapter knows which role.

const result = await gateway.complete({ transcript, maxTokens: spec.maxTokens, tools }, options);
// …failure handling unchanged from exercise 06…
transcript.push({ from: "model", text: reply.text, calls: reply.calls });
if (reply.stop !== "wants_tool") return report("landed", modelCall, [ … ]);

const results = reply.calls.map((call) => runTool(call, spec.allowedTools));
transcript.push({ from: "tools", results });

The model's turn is pushed before the tools run. Drop it and the next request answers a question the provider has no record of. One turn carries every result, in the order the model asked, because a reply may hold several tool_use blocks.

The transcript belongs to Hermes. The API keeps no memory between requests, so every model call resends the whole conversation, and the tools array with it. Part A measures what the transcript costs. Request 1 reports input_tokens: 23 and request 2 reports 110, for the same job. The mock estimates from the messages alone, so that rise is the transcript. A real provider bills the tool declarations as well.

allowedTools now has two readers. It decides which tools are declared, so an unlisted tool never reaches the model. It is also checked again when a call comes back, because a reply is model output and can name anything at all. Part B measures that second check.

graph_writeback → refused        // in the catalogue, absent from allowedTools
turns sent per model call: [ 1, 3 ]
  model call 1: operator
  model call 2: operator → model → tools

The refusal travels as a tool_result with is_error set, and the model tries something else. A refused tool is an answer, not a crash.

If you keep only four sentences from this lesson, keep these. A reply can ask for a tool, stop_reason reads tool_use, and Hermes runs the tool rather than the provider. The answer goes back as a tool_result block, keyed by tool_use_id, inside a user message. The API remembers nothing, so every model call resends the transcript and pays for it again. The spec decides which tools are declared, and Hermes checks the name again when the call comes back.
