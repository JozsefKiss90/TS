LangGraph.js, Evaluated

LangGraph.js can run lab 12's graph. Which parts of lab 12's interpreter does it take over, and which parts stay Hermes's code?

Why this matters for Hermes Scenario step S3 (dispatch under the graph) runs here on a framework. S5 (the loop iterates) is replayed where a held call waits. The win: lab 12's 74 tests pass unchanged with its interpreter replaced by LangGraph.js.

1 · The port is a signature

Lesson 0003 met the client SDK as a layer over work you had already done by hand. LangGraph.js is the same kind of layer over lab 12's interpreter. It runs a graph of functions, and it can save and pause the run. Lab 13 puts it behind the function lab 12 already calls.

// 13-graph-orchestration/src/langgraph-runner.ts
import type * as Lab12 from "../../12-workflow-graph/src/interpreter.js";

export const runGraph: typeof Lab12.runGraph =
  async (graph, guards, handlers, from, ctx, options) =>
    orchestrate(graph, guards, handlers, ctx, { job, checkpoints }).start(from, randomUUID());

The type typeof Lab12.runGraph makes the compiler check the runner against lab 12's declaration. A signature tells TypeScript what may be called. The implementation does the runtime work. The framework takes work away from your application code, not away from TypeScript.

The swap happens in vitest.config.ts. A small plugin replaces lab 12's interpreter.ts with the runner wherever any file imports it. That covers lab 12's test files and lab 12's handlers.ts, which startJob drives through. Lab 12's 74 tests then run in lab 13, byte for byte, and all 74 pass.

Thirty of the 74 reach runGraph, and the other 44 never call it. A green run means something only if the swap happened. tests/port.test.ts checks that the module lab 12 imports is the runner. With the plugin removed, both of its tests fail.

New today. Four ideas are new.

  • A framework can stand behind a signature you own, and your old tests measure it.
  • The framework picks the next node, and a router asks Hermes's guards first.
  • The framework's pause needs its own record of the run, beside lab 12's checkpoint.
  • Resumed by the framework, the paused node runs again from its first line.

Reprise: the SDK as a layer (0003), the port (0006), the interpreter and checkpoint (0018), the park (0019).

A conditional edge is an edge whose target a router function picks at run time from a fixed list. The declaration has two overloads. One takes the three values as arguments, the other takes one options object. Both return the builder, so the return type does not depend on the choice.

// @langchain/langgraph 1.4.21, dist/graph/graph.d.ts, abridged
addConditionalEdges(source: BranchOptions<…>): this;
addConditionalEdges(source: N, path: RunnableLike<RunInput, BranchPathReturnValue>,
                    pathMap?: …): this;

// lab 13, one call per node
builder.addConditionalEdges(node, (s) => {
  const edge = findOpenEdge(graph, guards, s.at.node, s.wanted.to, s.wanted.event);
  return edge.ok ? s.wanted.to : END;
}, [...targetsInTheGraphFile, END]);

The router is lab 12's question, asked by lab 12's findOpenEdge. The framework decides which function runs next, and the guards still decide whether the move is allowed. With that question removed, 2 tests fail. Both expect a guard to refuse.

The node the router picks makes the move. Its first act adds one to the step and saves lab 12's checkpoint through the port. A refused move goes to END, so no node arrives and nothing is saved. The router cannot write state, so the runner names the refusal by asking findOpenEdge again after the run. With the save removed, 14 tests fail.

4 · Two ways to resume

A checkpointer is the LangGraph.js object that saves the framework's state after each step of a run. A thread is the id under which the checkpointer groups one run's records. The function interrupt() refuses to run without a checkpointer.

Under the port, each runGraph call gets a fresh MemorySaver and a new thread. Nobody continues that thread. Lab 12 resumes a parked job from its own checkpoint, on a new call. So the port moved traversal to the framework, and left the stored record and the resume with Hermes.

The framework has its own resume. A node calls interrupt(value), and the run pauses. A later invoke(new Command({ resume: answer })) on the same thread continues it, and interrupt() returns the answer. Read the declaration first.

// @langchain/langgraph 1.4.21, dist/interrupt.d.ts
declare function interrupt<I = unknown, R = any>(value: I, options?: InterruptOptions): R;

// lab 13, inside the node, when the handler parks
const answer = interrupt(at, { responseSchema: z.enum(["approved", "denied"]) });
step = await handler({ ...at.state, verdict: answer }, ctx);

The return type R defaults to any, because the signature cannot know what an operator will send. The responseSchema option makes the framework parse the answer with Zod first. Part c sends "maybe", and the parse refuses it. The trace stays at four lines.

Part b runs the audit with graph_health held. It pauses at step 4 after one model call, and two records say the job waits: the framework's thread, and lab 12's queue. Resumed with "approved", it lands at 2 calls and 80 tokens, with a legal and complete trace.

Lab 12's checkpoint steps read 1, 2, 3, 4, 4, 5, 6, 7, 8. The framework restarts the paused node from its first line, and that line saves the arrival at step 4. The save is the same both times. A side effect before the pause would repeat.
