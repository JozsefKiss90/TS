1 · One run through Hermes, end to end

Before any more architecture words, watch one job cross the intended system. This is the Hermes Spec-to-Evidence Loop from MISSION.md — validated TaskSpec → bounded planning → Graph RAG evidence → approved tool execution → evaluation → durable trace — told as nine moments in the life of one task. The guiding principle it implements: put probabilistic reasoning inside a deterministic, typed, observable control system. The model is the probabilistic part; everything numbered below is the deterministic shell around it.

  1. A task arrives as untrusted input — bytes, not facts.
  2. Hermes validates it into a TaskSpec — lesson 0005's parse applied to work itself; invalid work is rejected before a token is spent (S1).
  3. The supervisor — the control loop's deterministic core — reads the spec's constraints and decides the next permitted action.
  4. A routing decision selects a model route for this step: which provider, which model, at what cost class.
  5. The supervisor calls ModelGateway.complete(...) — the port from lesson 0006 (S4).
  6. The provider adapter translates the call and invokes the SDK; the SDK does its mechanics on the wire.
  7. The result comes back as provider-neutral data — a GatewayResult, proof or classified failure, never an exception.
  8. The supervisor decides what that result means: continue the loop, retry later, request approval, stop, or record failure.
  9. Evidence, decisions, usage, and request identifiers enter the durable trace — what Hermes did, replayable (S7).

2 · "Policy," defined operationally

Lesson 0006 leaned on the word "policy" in nearly every section; here is the definition it deserves:

A Hermes policy is a deterministic rule that converts validated facts — about a task, the loop's state, or an external result — into a permitted next action or a terminal outcome. Deterministic: same facts, same decision, every time. Validated facts: nothing crosses into a policy rule without a runtime check (lesson 0005) or a compile-time contract (lesson 0006). Permitted: the output is always an action Hermes is allowed to take, or a terminal state — never "whatever the exception unwound to."

The word earns its keep only if it excludes things. Four neighbours get mistaken for policy, plus the wire beneath them all — learn to tell the five apart and lesson 0006's "mechanics below, policy above" becomes a precise sentence instead of a slogan:

Against those five, the policy in exercise 05 is easy to point at: "a throttled call means this job is parked and retried later" and "a malformed reply means give up and book zero tokens" are rules converting a classified fact into a job outcome. They live in supervisor.ts and nowhere else.

Deconfusion: "above" and "below". These words describe architectural dependency and responsibility — which files may import which vocabulary, and who owns which decision. They do not mean: security layers (nothing is hidden — the adapter imports the SDK in plain sight), physical location (every file sits in the same src/), or call-stack height (at runtime the supervisor's frame sits under the adapter's on the stack while awaiting it — the call stack is upside-down relative to the architecture diagram, and that is fine, because the diagram was never about the stack). "Above the port" = imports only gateway.ts, speaks only domain vocabulary. "Below the port" = implements gateway.ts, may speak provider vocabulary, must translate before crossing up.

3 · The policy that exists today: superviseOneCall, traced honestly

Open hermes-sdk-lab/05-model-gateway/src/supervisor.ts and count the actual decisions. There are exactly five, one per arm of the result union — every one meets §2's definition (validated fact in, terminal outcome out):

  • Success → landed, and the ledger books validated usage only. tokensSpent: usage.inputTokens + usage.outputTokens — numbers that passed the adapter's boundary parse; exercise 04's "1142" string-concat corruption cannot reach this line.
  • throttled → retry_later. The provider's backoff request is a fact; "park the job" is the rule's output.
  • aborted → gave_up — the operator's kill is terminal for this one-call world.
  • malformed_reply → gave_up, booking zero tokens — a lying ledger is worse than an empty one, so an unproven reply contributes nothing to the count.
  • transport / rejected → gave_up — with the detail preserved in notes for a human to read.

Call this what it is: a policy seed — the smallest real instance of the supervisor's job, planted where the full organ will grow. Deconfusion, per house rule: seed does not mean "small version of everything." It classifies one model-call result into a report. It does not loop, route, budget, gate, or persist. The full picture:

4 · Wiring is not routing

The sentence in lesson 0006 most likely to be over-read is "routing is policy, decided above." Here is the evidence of what actually exists — main.ts, verbatim (abridged):

const MODEL = "claude-opus-4-8";

const client = new Anthropic({ baseURL: BASE_URL, apiKey: API_KEY, ... });
return new AnthropicModelGateway(client, MODEL);

Read it for what it is:

  • This is static composition — wiring. main.ts is the exercise's composition root: the one place that knows concrete classes exist and bolts them together. The model id is a constant; nothing chooses it at runtime.
  • Passing MODEL into the adapter's constructor prevents the adapter from owning model selection — the adapter cannot hardcode a model, so whoever constructs it decides. That is a real architectural move: the decision point was placed above the port.
  • It does not prove a dynamic routing policy exists. A constant is not a decision rule (§2: no facts in, no rule, no policy — just configuration).
  • Illustrative only: a future router might hold several configured gateways and select one from a validated task's requirements, cost class, or capability needs — a rule converting facts into a choice, which would meet §2's definition. No such router exists anywhere in this repository, no roadmap row schedules it, and this primer does not design it.
The one-sentence version, worth memorizing: Lesson 0006 reserves model selection for policy; it does not yet implement model-selection policy.

5 · The layer stack, file by file

Part A's single call, as a runtime trace through the layers — every hop is a file you have open:

supervisor                       superviseOneCall()          policy
→ ModelGateway.complete(...)     the port's signature        contract (erased at runtime)
→ AnthropicModelGateway.complete the adapter                 translation + boundary validation
→ client.messages.create(...)    the SDK                     mechanics
→ SDK transport                  fetch, serialization        mechanics
→ HTTP API                       POST /v1/messages (:8787)   the wire

State each layer's nature precisely, because two of these lines are easy to misread:

  • ModelGateway is an erased TypeScript interface. At runtime it does not exist: it never calls the SDK, never routes, never wraps. The type-checker enforced it at build time, at every implements and every import — then deleted it.
  • AnthropicModelGateway is the runtime object that actually executes: it holds the SDK client, translates the call down, runs the SDK, parses the reply at the boundary, and translates the result up.
  • main.ts chooses and injects the implementation. The supervisor receives "some ModelGateway" and cannot tell which — swap in FakeModelGateway and it runs identically (Part C, measured: 0.6 ms, mock stopped).
  • The port defines Hermes vocabulary; the adapter translates that vocabulary into Anthropic requests and translates validated provider results back.

The deliberately ambiguous one, resolved. "Retry" names two different things in that matrix, and conflating them is the classic layer mistake. The SDK's automatic retry re-sends one HTTP operation inside one complete() call — the supervisor never learns it happened, no job state changes, and the whole affair is responsibility ⑤ mechanics. The supervisor's retry_later is a job-level decision: this unit of work is parked, its report says so, and something above (today: you, reading the report; later: the loop of lessons 0008+) will resume it. Same English word; different layer, different owner, different lifetime. When both fire — default maxRetries: 2 against a persistent 429 — the SDK retries twice (mechanics, ~10 s), gives up, the adapter classifies (translation), and then the supervisor parks the job (policy). Each layer did its own kind of retry-shaped work without ever borrowing the other's.

7 · Why provider-neutral types earn their keep — here, specifically

The weak argument for the port's neutral vocabulary is "another provider might someday be added." The course did not use it, and neither should you — MISSION rules out speculative work, and no requirement names a second provider. The strong arguments are all about the system that exists today:

  • The supervisor classifies domain facts, not provider classes. Its switch reads failure.kind, not err instanceof RateLimitError — so policy rules are written once, in Hermes's own words, and survive any change below the port.
  • The same policy runs against AnthropicModelGateway and FakeModelGateway. Measured: Part C drives the identical retry_later branch B1 drove over the wire, in 0.6 ms, mock stopped. Offline-testable policy is Phase 1's exit criterion, and neutral types are what make it possible.
  • Provider response validation stays at the external boundary. The one place unproven bytes exist is inside the adapter, and that is where WireReplySchema lives. Above the port, types are proof.
  • SDK upgrades cannot silently redefine domain vocabulary. If 0.114.0 renamed a field or added a stop_reason, the breakage lands in one adapter file — the supervisor's words (completed, throttled) are Hermes's to keep.
  • Exhaustive switching over GatewayFailure forces decisions. Add a failure kind to the port and the supervisor fails to compile until Hermes has decided what that failure means for a job. The type system turns "we forgot to handle it" into a build error.

And the honest risk, stated as lesson 0006 §4 stated it: a port designed against one provider can still grow provider-shaped — vocabulary that looks neutral but silently mirrors Anthropic's model. FakeModelGateway supplies a second implementation and therefore some standing pressure against this: every time the fake satisfies the contract trivially, it re-demonstrates that nothing in the signature requires Anthropic. But keep the claim inside its evidence: the fake is a second implementation — a test double, not a second provider, and it does not constitute proof of interoperability with any real provider. That proof would take a second live adapter, which nothing currently justifies building.
