# Demonstrated: the JSON boundary — runtime validation, safeParse-as-data, and the phantom ledger breach

Closed-book recall for lesson 0005 §8 (*Say it in your own words*), collected 2026-07-29. All four prompts answered correctly and completely; no misconceptions found. This is the strongest single recall of Phase 0 — the learner not only reproduced the mechanics but derived the "silent corruption is worse than a loud false alarm" argument unprompted (§8 Q4's *why worse*).

**Evidence per question:**

- **Q1 (runtime validation + type erasure + why non-optional at a JSON boundary):** [[runtime-validation]] defined as "the execution-time inspection of an actual value to determine whether it satisfies a declared contract"; [[type-erasure]] as TypeScript removing "interfaces, type aliases, and assertions when compiling to JavaScript, so they perform no checks while the program runs." The join is exact: "JSON arrives as untrusted runtime data, while the TypeScript types that describe its expected shape no longer exist to inspect it" — the erased contract cannot police the byte stream, so a real check must. → promoted [[runtime-validation]] (introduced lesson 0001, "used in anger" at last). [[type-erasure]] already demonstrated.

- **Q2 (walk the pipeline; name what replaced `as` and what it is at runtime):** Before — `wire bytes → JSON.parse → unknown → as MessageResponse → supposedly typed code`, with the correct verdict that the assertion "changed only TypeScript's view of `body`. At runtime, `as MessageResponse` became nothing." After — `→ unknown → MessageSchema.safeParse(body) → {failure → issues | success → result.data} → trusted, typed code`. Named exactly what replaced the `as`: `const result = MessageSchema.safeParse(body)`, and what it is at runtime — "`MessageSchema` is a real Zod schema object containing executable validation rules; `safeParse()` applies those rules to the actual value; `result.data` is the validated, schema-shaped value." → promoted [[type-assertion]] (already demonstrated) reinforced; [[zod-schema]] (the runtime object with executable rules) and [[json-boundary]] (the parse-once-at-the-edge rule) demonstrated → promoted.

- **Q2b ([[schema-inference]]):** unprompted-precise on `type Message = z.infer<typeof MessageSchema>` — "`z.infer` does not validate anything at runtime; it prevents the TypeScript type and runtime schema from becoming separate, drifting definitions." Caught that the arrow points *from* schema *to* type (the lesson's §4 framing) and that its whole job is drift-prevention, not checking. → promoted [[schema-inference]].

- **Q3 (`parse` vs `safeParse`; which S1 wants; why rejection-as-data beats an exception):** `parse` returns validated `Message` on success but throws `ZodError`; `safeParse` "always returns a discriminated result" — reproduced the union verbatim as `{ success: true; data: Message }` / `{ success: false; error: ZodError }` and the guard `if (!result.success) return { accepted: false, issues: result.error.issues }`. S1's Job Envelope check wants `safeParse` "because an invalid envelope is an expected rejection outcome, not necessarily an exceptional program failure." The supervisor argument is complete and non-generic: path-addressed issues (`stop_reason`, `usage.output_tokens`) let it "identify which fields failed; record all problems rather than stopping at an opaque error; reject the job before spending model tokens; attach the rejection to logs or evidence; distinguish invalid input from infrastructure failure" — closing with the real distinction that an exception "first interrupts ordinary control flow," whereas `safeParse` "makes rejection an explicit branch in the supervisor's protocol." → promoted [[safe-parse]]; and finally → promoted [[discriminated-union]] and [[narrowing]] on exactly the evidence 0007 was holding them for (the success/failure union and its `if (!result.success)` guard).

- **Q4 (the ledger measurement; why the same bug with different digits is worse):** the phantom breach reconstructed step by step — the wire's `output_tokens: "42"`, the assertion claiming `number` without converting, `11 + "42"` concatenating (because "once either operand of `+` is a string, JavaScript performs concatenation") to `"1142"`, the ceiling comparison coercing back so `"1142" > 1000 === true` — a phantom 1,142 against a real spend of `11 + 42 === 53`. Then the derived insight, which is the point of the question: `11 + "4" === "114"` (actual 15) with `"114" > 1000 === false` raises **no** alarm, so "a plausible silent error is more dangerous" than the conspicuous false alarm — it can "contaminate budgeting, reporting, routing, or later supervisory decisions" undetected. This is precisely why S1/S2 parse at the edge instead of trusting coercion downstream.
