Signature Trace: From new Anthropic() to Message

Expand one SDK call until every object, method, parameter, return type, and runtime hand-off is visible. The goal is not to memorize declarations; it is to see exactly how the SDK moves API chores out of your application code.

Version pin Every SDK declaration and implementation excerpt in this supplement was verified against @anthropic-ai/sdk 0.113.0. Generated SDK surfaces change. To reproduce the same signatures, use the exact dependency "@anthropic-ai/sdk": "0.113.0", without ^ or ~. The excerpts are abridged only where marked; omitted members do not change the reasoning shown.

How to use this supplement

Read it after Lesson 0001, revisit the Lesson 0002 section after completing the raw client, and finish the Lesson 0003 section beside the SDK client. The trace starts from the expression you write:

const client = new Anthropic(options);
const message = await client.messages.create(params, requestOptions);
The distinction to preserve throughout A signature tells TypeScript what may be called and what type comes back. It does not authenticate, serialize, send, retry, parse, or validate anything. The installed JavaScript implementation performs those runtime operations. The SDK abstracts responsibilities away from your application code, not away from TypeScript.

Lesson 0001 supplement · Read the call as an object path

1. Import the class

import Anthropic from "@anthropic-ai/sdk";

The default import gives the local name Anthropic to the SDK's exported class. A class describes what its instances contain and can do. At this point no client exists and no HTTP request has been sent.

2. Call the constructor

The relevant declaration in client.d.ts is:

export declare class Anthropic extends BaseAnthropic {
  messages: API.Messages;
  // other resources omitted
}

// Inherited construction signature, abridged:
constructor(options?: ClientOptions);

Now read the expression:

const client = new Anthropic({
  apiKey: "mock-key",
  baseURL: "http://localhost:8787",
});
SyntaxMeaningWhat exists at runtime?
AnthropicThe class imported from the packageA constructor function
new Anthropic(...)Invoke its constructorA new client object
{ apiKey, baseURL }One argument shaped as ClientOptionsA plain object read by the constructor
clientA variable inferred as type AnthropicA reference to the client instance

Construction configures durable defaults. It still does not create a model response. In 0.113.0 the implementation stores defaults such as timeout and maxRetries, resolves how authentication will work, and creates resource objects including:

// Runtime implementation, simplified from client.mjs:
this.messages = new API.Messages(this);

The parent client is passed into the Messages resource. That retained reference is why messages.create() can later use the client's base URL, authentication, timeout, retry policy, and transport without receiving them all again.

3. Follow the resource property

client.messages

This is property access, not a network call. Its declared type is API.Messages, the SDK resource corresponding to the Messages API. The next dot selects a method on that object:

client.messages.create

Only the parentheses invoke the method:

client.messages.create(params, requestOptions)

4. Read a method signature from left to right

For a non-streaming request, 0.113.0 declares:

create(
  params: MessageCreateParamsNonStreaming,
  options?: RequestOptions,
): APIPromise<Message>;
Signature fragmentQuestion it answers
createWhich method am I calling?
params:What is the first argument called?
MessageCreateParamsNonStreamingWhich shapes may the first argument have?
options?:Is the second argument optional?
RequestOptionsWhich shapes may the second argument have?
APIPromise<Message>What value is returned immediately?

The two arguments have different jobs:

client.messages.create(
  {
    model: "claude-opus-4-8",
    max_tokens: 100,
    messages: [{ role: "user", content: "Hello" }],
  },                                      // params: what the API should generate
  {
    maxRetries: 0,
    timeout: 2_000,
    signal: controller.signal,
  },                                      // options: how this HTTP operation should run
);

APIPromise<Message> says that the operation is asynchronous and that parsing it normally produces a Message. It does not mean a Message already exists at the moment create() returns.

5. Let await unwrap the operation

const operation = client.messages.create(params);
// operation: APIPromise<Message>

const message = await operation;
// message: Message & { _request_id?: string | null }

In this release, APIPromise<T> is declared as a specialized subclass of Promise<WithRequestID<T>>. Because Message is an object, WithRequestID<Message> adds an optional SDK property:

type WithRequestID<T> =
  T extends Record<string, any>
    ? T & { _request_id?: string | null }
    : T;

This is why await gives your code the parsed message, not the promise wrapper. The optional _request_id does not belong to Anthropic's JSON message document; the SDK derives it from the HTTP request-id response header.

Lesson 0001 checkpoint

  1. Anthropic is the class; client is one configured instance.
  2. client.messages is a resource property, not the returned model message.
  3. .create(...) begins an asynchronous API operation.
  4. The signature describes the call; the implementation performs it.
  5. await converts your view from “operation in progress” to “parsed result.”

Lesson 0002 supplement · What raw fetch leaves to you

1. Start with the generic transport signature

The built-in fetch API is deliberately unaware of Anthropic:

fetch(
  input: RequestInfo | URL,
  init?: RequestInit,
): Promise<Response>;

Its return type says only that an HTTP response will eventually exist. It cannot infer from the URL that the body should be an Anthropic Message. Consequently, the raw client must own every Anthropic-specific decision:

const response = await fetch(`${BASE_URL}/v1/messages`, {
  method: "POST",
  headers: {
    "content-type": "application/json",
    "x-api-key": API_KEY,
    "anthropic-version": "2023-06-01",
  },
  body: JSON.stringify(params),
  signal: controller.signal,
});

2. Parsing JSON does not discover an Anthropic type

The relevant conceptual pipeline is:

const value = await response.json();

In the raw exercise you supplied the missing Anthropic knowledge yourself:

interface MessageResponse {
  id: string;
  type: "message";
  role: "assistant";
  content: Array<{
    type: string;
    text?: string;
  }>;
  stop_reason: string | null;
  usage: {
    input_tokens: number;
    output_tokens: number;
  };
}

const body = (await response.json()) as MessageResponse;

The assertion as MessageResponse does not:

  • parse the response—response.json() already did that;
  • check that id, content, or usage exists;
  • check the value of type;
  • change the runtime object;
  • add authentication, retries, timeouts, or cancellation.

It tells the compiler to trust your claim. Valid JSON with the wrong shape can therefore pass parsing:

{ "banana": 42 }

and fail later when the application trusts body.content.

3. The handwritten interface and the SDK type have equal runtime force

The real difference is provenance, completeness, and maintenance—not stronger runtime proof.

5. Editor diagnostic, type-check, and execution are three different events

The lesson experiment with mesages needs one precise qualification:

client.messages.create({
  model,
  max_tokens: 100,
  mesages: [{ role: "user", content: "Hello" }],
});
  • VS Code's TypeScript language service can underline the typo immediately.
  • pnpm typecheck can report it through tsc and exit unsuccessfully.
  • tsx src/client.ts transpiles and runs without performing a complete type-check.

Therefore the typo is prevented from reaching the mock only when type-checking is an enforced gate, for example:

{
  "scripts": {
    "request": "tsc --noEmit && tsx src/client.ts"
  }
}

If you run only tsx, the erased TypeScript types cannot stop JavaScript from sending the malformed body. The mock may then answer with the runtime 400 that the editor already predicted.

Lesson 0002 checkpoint

  1. fetch() knows HTTP, not the Messages API.
  2. response.json() checks JSON syntax, not the MessageResponse shape.
  3. A TypeScript interface constrains your code only while type-checking runs.
  4. The raw client owns the six responsibilities explicitly.

Lesson 0003 supplement · Expand the SDK abstraction

1. Constructor signature: client-wide defaults

The actual ClientOptions interface in 0.113.0 is larger. These are the members that account for the Lesson 0003 client:

interface ClientOptions {
  apiKey?: string | ApiKeySetter | null | undefined;
  authToken?: string | null | undefined;
  baseURL?: string | null | undefined;
  timeout?: number | undefined;
  maxRetries?: number | undefined;
  defaultHeaders?: HeadersLike | undefined;
  fetch?: Fetch | undefined;
  // additional members omitted
}

constructor(options?: ClientOptions);
OptionCompile-time contributionRuntime contribution
apiKeyAccepts the declared credential formsSupplies authentication; defaults can be resolved from configuration/environment
baseURLMust be a compatible string/nullish valueSelects the API host or local mock seam
timeoutMust be a number when suppliedLimits one request attempt in milliseconds
maxRetriesMust be a number when suppliedSets the client-wide retry count; default is 2
fetchMust match the expected fetch signatureReplaces the underlying transport implementation

The interface does not read an environment variable or arm a timer. The constructor implementation does that runtime work.

2. Resource signature: the endpoint becomes a method

The class exposes:

messages: API.Messages;

and the runtime Messages.create() implementation eventually delegates to:

// Simplified from resources/messages/messages.mjs:
return this._client.post("/v1/messages", {
  body,
  timeout: timeout ?? 600_000,
  ...options,
  headers: buildHeaders(/* SDK and per-request headers */),
  stream: params.stream ?? false,
});

This implementation is where the apparently absent endpoint reappears. The method name does not replace POST /v1/messages; it hides that repeated construction behind a resource method.

3. Params signature: the request body becomes a checked shape

The non-streaming params type is formed in two layers:

// Abridged from resources/messages/messages.d.ts:
interface MessageCreateParamsBase {
  max_tokens: number;
  messages: Array<MessageParam>;
  model: Model;
  // optional request-body fields omitted
}

interface MessageCreateParamsNonStreaming
  extends MessageCreateParamsBase {
  stream?: false;
}

These declarations explain the editor and tsc diagnostics:

  • max_tokens, messages, and model are required;
  • mesages is not a known property;
  • stream?: false selects the non-streaming overload;
  • nested MessageParam values also have declared role and content shapes.

This is compile-time representation of responsibility ④. At runtime the SDK still has to turn the params object into a JSON request body.

4. Options signature: transport behavior stays outside the body

The second argument uses RequestOptions. Relevant members in 0.113.0 are:

interface RequestOptions {
  headers?: HeadersLike;
  maxRetries?: number;
  timeout?: number;
  signal?: AbortSignal | undefined | null;
  fetchOptions?: MergedRequestInit;
  // internal and advanced members omitted
}

Keeping this object separate prevents transport mechanics from leaking into the Messages API JSON contract:

await client.messages.create(
  {
    model,
    max_tokens: 100,
    messages,
  },                         // serialized into the request body
  {
    maxRetries: 0,
    timeout: 200,
    signal,
  },                         // controls the SDK operation; not model input
);

The same option at two scopes establishes override precedence:

const client = new Anthropic({ maxRetries: 2 }); // default for this client

await client.messages.create(params, {
  maxRetries: 0,                                  // override for this call
});

5. Overloads: arguments select the return type

Version 0.113.0 declares three create() signatures:

create(
  params: MessageCreateParamsNonStreaming,
  options?: RequestOptions,
): APIPromise<Message>;

create(
  params: MessageCreateParamsStreaming,
  options?: RequestOptions,
): APIPromise<Stream<RawMessageStreamEvent>>;

create(
  params: MessageCreateParamsBase,
  options?: RequestOptions,
): APIPromise<Stream<RawMessageStreamEvent> | Message>;

An overload is not three runtime methods with the same name. It is one implementation described by multiple call signatures. TypeScript selects the most specific description it can from the argument:

ParamsSelected compile-time return type
No stream, or stream: falseAPIPromise<Message>
Literal stream: trueAPIPromise<Stream<RawMessageStreamEvent>>
A boolean not known to be true or falseThe union of both possible results
Boundary with Lesson 0004 Lessons 0001–0003 follow the first overload only. The second overload is shown here so Lesson 0004 begins from a familiar method rather than an unexplained new message type. stream: true changes the successful response representation and lifecycle; it does not define a second final Message shape.

6. APIPromise<Message>: the operation and parsing boundary

The declaration is:

class APIPromise<T> extends Promise<WithRequestID<T>> {
  asResponse(): Promise<Response>;

  withResponse(): Promise<{
    data: T;
    response: Response;
    request_id: string | null | undefined;
  }>;

  // other members omitted
}

This gives you three alternative views of an operation:

const message = await client.messages.create(params);
// parsed Message + optional _request_id

const raw = await client.messages.create(params).asResponse();
// raw Fetch Response

const both = await client.messages.create(params).withResponse();
// parsed data + Response + request_id

The runtime parser in 0.113.0 effectively does:

const contentType = response.headers.get("content-type");

if (contentType indicates JSON) {
  const json = await response.json();
  return addRequestID(json, response);
}

addRequestID() defines _request_id as a non-enumerable property using the request-id header. The generic return type tells TypeScript to treat the parsed value as T; ordinary non-streaming parsing does not perform field-by-field validation against Message.

7. Message: the returned contract

The response interface in 0.113.0 is larger than the mock fixture. Its central shape is:

// Abridged from resources/messages/messages.d.ts:
interface Message {
  id: string;
  container: Container | null;
  content: Array<ContentBlock>;
  model: Model;
  role: "assistant";
  stop_details: RefusalStopDetails | null;
  stop_reason: StopReason | null;
  stop_sequence: string | null;
  type: "message";
  usage: Usage;
}

This is the complete assistant-response object—not one input turn and not one stream event. Notice that content is an array of a union type:

type ContentBlock =
  | TextBlock
  | ThinkingBlock
  | RedactedThinkingBlock
  | ToolUseBlock
  | ServerToolUseBlock
  | WebSearchToolResultBlock
  | WebFetchToolResultBlock
  | CodeExecutionToolResultBlock
  | BashCodeExecutionToolResultBlock
  | TextEditorCodeExecutionToolResultBlock
  | ToolSearchToolResultBlock
  | ContainerUploadBlock;

The literal type property discriminates among these shapes. That is why access to .text requires narrowing:

for (const block of message.content) {
  if (block.type === "text") {
    console.log(block.text);
  }
}

Before the check, block might be any ContentBlock. Inside the branch, TypeScript knows it is a TextBlock. Lesson 0004 reuses exactly this idea for unions of stream events.

8. Typed errors: runtime classes not shown in the success return type

TypeScript has no checked-exception syntax, so APIPromise<Message> does not list every error that may be thrown. The SDK supplies a runtime class hierarchy instead:

AnthropicError
└── APIError
    ├── APIUserAbortError
    ├── APIConnectionError
    │   └── APIConnectionTimeoutError
    ├── BadRequestError            // status 400
    ├── AuthenticationError        // status 401
    ├── PermissionDeniedError      // status 403
    ├── NotFoundError              // status 404
    ├── ConflictError              // status 409
    ├── UnprocessableEntityError   // status 422
    ├── RateLimitError             // status 429
    └── InternalServerError

These classes allow runtime narrowing:

try {
  const message = await client.messages.create(params);
} catch (error: unknown) {
  if (error instanceof Anthropic.RateLimitError) {
    console.error(error.status);                       // typed as 429
    console.error(error.requestID);
    console.error(error.headers.get("retry-after"));
  } else if (error instanceof Anthropic.APIUserAbortError) {
    console.error("Cancelled by the caller");
  } else if (error instanceof Anthropic.APIConnectionTimeoutError) {
    console.error("One or more attempts timed out");
  } else if (error instanceof Anthropic.APIError) {
    console.error(error.status, error.type, error.requestID);
  } else {
    throw error;
  }
}

The declaration exposes properties such as status, headers, error, requestID, and type. The implementation decides when to construct and throw each class.

9. Retry behavior: mechanics behind two small signatures

The retry behavior is controlled by the same property at two levels:

new Anthropic({ maxRetries: 2 })                    // client default

client.messages.create(params, { maxRetries: 0 })  // per-call override

In 0.113.0, the runtime implementation retries eligible connection failures and HTTP statuses including 408, 409, 429, and 5xx while attempts remain. If a response supplies retry-after-ms or retry-after, the implementation derives the delay from that header; otherwise it calculates exponential backoff with jitter.

The raw client could read and print retry-after. The SDK's implementation can obey it, wait, issue the next attempt, and expose only the eventual success or final typed error to your application. With maxRetries: 2, the maximum is three attempts: one initial request plus two retries.

11. What the future ModelGateway must still own

The SDK provides mechanisms, not Hermes policy. A gateway must still decide matters such as:

  • which model is allowed for a task and when fallback is permitted;
  • token and monetary budgets;
  • application-specific retry limits and idempotency rules;
  • approval requirements before consequential actions;
  • runtime validation of model-generated structured output before Hermes trusts it;
  • logging, evidence capture, redaction, and failure reporting required by the Spec-to-Evidence Loop.

maxRetries is a mechanism. “This class of Hermes operation may retry once within its remaining budget” is policy. Message is an API response type. “This generated object satisfies the task schema and is safe to use” requires a separate runtime validation policy.

  2. Compile time: It selects the non-streaming create() overload because the params omit stream or use stream: false.
  3. Compile time: It checks required params and the separate request-options shape.
  4. Runtime: create() delegates to the parent client's POST /v1/messages implementation.
  5. Runtime: The client resolves its URL, authentication, version and other headers.
  6. Runtime: It serializes the body and begins the HTTP attempt with timeout and abort plumbing.
  7. Runtime: Eligible failures are retried according to per-call or client defaults, honoring retry headers when present.
  8. Runtime: A successful JSON response is parsed into a plain JavaScript value.

Self-check

1. Which part sends the request: the create() signature or its implementation?

The JavaScript implementation. The signature only describes the legal call and its inferred return type.

2. Why is client.messages not the Message response?

client.messages is a long-lived Messages resource object containing methods such as create(). A response Message is the result of one completed create operation.

3. Why can VS Code show a typo while tsx still sends it?

The editor runs TypeScript analysis, while tsx can transpile and execute without enforcing a full type-check. Only an enforced tsc gate prevents execution.

4. What does APIPromise<Message> add beyond a plain Promise<Message>?

In 0.113.0 it adds SDK response helpers such as asResponse() and withResponse(), and its normal parsed result uses WithRequestID<Message>.

5. Does Message validate the incoming JSON at runtime?

No. Normal non-streaming parsing validates JSON syntax, then the SDK's generic return type supplies the compile-time contract. The type itself is erased at runtime.

6. What changes when stream: true is added?

A different overload is selected: APIPromise<Stream<RawMessageStreamEvent>>. Lesson 0004 explains the corresponding SSE response lifecycle and reconstruction of a final Message.
